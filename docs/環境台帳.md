## C-3. プレミアム判定の方法（重要・次回も使う）

一覧の見た目だけでは可否が判断できない。以下で確定させる。

```
1. 非プレミアムのトリガー（例: Recurrence）でフローを作る
2. 対象のアクションを追加する（パラメータは未入力でよい）
3. フローチェッカー（聴診器アイコン）を開く
4. 「警告(0)」であれば、そのアクションは標準
```

**「エラー」は必須パラメータ未入力によるもので、可否とは無関係。**

## C-4. 「選択したファイルの場合」の設定時の注意

- **サイト アドレス欄には、サイトのルートまでを入れる**
  （ライブラリまでのフルパスを入れると「検索と一致する値がありません」になる）
- サイトを選ぶと **ライブラリ名の欄が現れる**ので、そこでライブラリを指定する

## C-5. コネクタの認証方式

Power Automate のコネクタは **OAuth による「接続」** を単位として認証情報を保持する。
**フローは常に「接続を作成した人」の権限で実行される。**

| 影響 | 内容 |
|---|---|
| **参照範囲** | 接続作成者が見られる範囲のみ。共有フォルダ／共有サイトを使う設計にする |
| **権限の貸与** | フローを起動できる人は、実質的に接続作成者の権限で操作できる |
| **可用性** | 接続作成者の異動・退職・パスワード変更でフローが停止する |
| **登録者列** | フロー経由の行は `登録者` が接続作成者になる。**実際の起票者を保持する列を別途持つこと** |

## C-6. Teams投稿者の指定

投稿アクションには **「投稿者」** パラメータがあり、**フロー ボット** と **ユーザー** から選べる。

**台帳の通知は「フロー ボット」を使う。** いずれの名義でもメンションは正しく届く。

# X. グリッドビューへの貼り付け（不採用の根拠）★重要

## X-1. 症状

| 条件 | 結果 |
|---|---|
| Person型を含まない列のみ | **即座に入力される**（PC2） |
| **Person型（メールアドレス）を含む** | **直後にブラウザが応答不能になる**（PC1・PC2ともに再現） |
| 全列（PC1） | 応答不能。PC1は列を減らしても重い |

3行程度のデータで発生。**行数の問題ではない。**

## X-2. 原因

Person型列への貼り付けで、メールアドレスから実在ユーザーを照会する処理が
**ブラウザ側で走り、そこで詰まる**と考えられる。

## X-3. 判定

**グリッドビューへの貼り付けは採用しない。**

理由:
1. **担当者は必ずPerson型で持つ**設計であり（Teamsメンションに必須）、
   その列に貼り付けられないなら方式として成立しない
2. **2台のPCで再現**しており、環境固有の問題ではない
3. 一部のPCでのみ固まる機能を全員配布のツールの主要導線に置けない

## X-4. 代替（即時性は確保できる）

貼り付けを採用した唯一の理由は「即時性」だったが、**手動フロー実行で代替できる**（§D-2）。

```
起票UI → JSONファイル出力
  → ライブラリへドラッグ＆ドロップ（数秒）
  → ファイルを選択 → Power Automate → 実行
  → 数秒で台帳へ反映
```

副次的な利点:

- 3リストへ順序どおり貼るという**間違えやすい操作が消える**
- Person型の解決は**サーバ側**で行われるため、ブラウザは固まらない
- **PCの性能に依存しない**
- 重複防止を起票IDで一元化できる
