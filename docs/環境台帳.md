# 環境台帳.md — 会社環境で判明した仕様の蓄積

このファイルは**このプロジェクトで最も価値のある資産**である。
復路（会社→自宅）が極細であるため、**一度分かったことを二度調べない**ために存在する。

## 記入ルール

- **判定は「可 / 不可 / 不明 / 未実施」のいずれかで書く**
- 推測で埋めない。分からないものは「不明」とする
- **業務データ、実在の案件名、個人名、社内URL、テナント名は書かない**（`PROJECT.md` §4）
- 社内固有のパスは種別のみ記す
- 判明した日付を記す

### 台帳の置き場所：**SharePointリストに確定**

理由:
- Person型・参照（Lookup）型が使え、3層構造を素直に実現できる
- SharePointトリガーが標準で揃っており、通知の自動化が成立する
- `SharePoint に HTTP 要求を送信します` が標準のため、リスト構築を自動化できる

Boxは**成果物ファイルの格納先**として併用する（`要件.md` §1 の想定どおり）。

# コネクタの認証方式（重要）

Power Automate のコネクタは **OAuth による「接続」** を単位として認証情報を保持する。
**フローは常に「接続を作成した人」の権限で実行される。**

## 設計への影響

| 影響 | 内容 |
|---|---|
| **参照範囲** | フローがアクセスできるのは、接続作成者が見られる範囲のみ。共有フォルダ／共有サイトを使う設計にする |
| **権限の貸与** | フローを起動できる人は、実質的に接続作成者の権限で操作できる。起動条件を絞る設計が必要 |
| **可用性** | 接続作成者の異動・退職・パスワード変更でフローが停止する。本番では共用アカウントでの接続作成を検討（社内規程の確認が必要） |
| **登録者列** | フロー経由で作成された行は、SharePointの `登録者` 列が接続作成者になる。**実際の起票者を保持する列を別途持つこと** |

## Teams投稿者の指定

Teams の投稿アクションには **「投稿者」** パラメータがあり、以下から選べる。

| 投稿者 | 見え方 |
|---|---|
| **フロー ボット** | ボット名義で投稿。個人名が出ない |
| ユーザー | 接続作成者の名前とアイコンで投稿される |

**台帳の通知は「フロー ボット」を使う。** ユーザー名義だと、全員への自動通知が
特定個人の手動送信のように見えてしまうため。なお、いずれの名義でもメンションは正しく届く。

# 想定外の発見・制約

- **サイト設定のトップに「ユーザーと権限」セクションが表示されない。**
  Teams連携サイトのため、権限管理がM365グループ側に寄せられている可能性がある。
  `_layouts/15/role.aspx` への直接アクセスで到達可能。

- **「HTTP 要求の受信時」がプレミアムであるため、起票UI（ローカルHTML）から
  Power Automate を直接呼び出せない。**
  代替として以下の2案がある。
  - **v1**: 起票UIが整形済みタブ区切りテキストを出力 → 人がグリッドビューに貼り付け
  - **v2**: 起票UIがJSONファイルを出力 → 人がBox/SharePointの所定フォルダに配置
    → 標準トリガーが発火 → `SharePoint に HTTP 要求を送信します` で3層構造を一括生成

  **v2は全て標準ライセンスで実現可能**であることが今回確認できた。

- Boxのトリガーは「プロパティのみ」だが、
  `パスによるファイル コンテンツの取得` が標準で使えるため中身も読める。
