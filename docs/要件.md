## 2. データ構造

### 2.1 3層構造

```
起票（親）              … 1回の依頼＝1件
 └ 部材群               … 起票時の入力単位
    └ 明細              … 部材1点＋数量。数量データの実体
        ↓ グルーピング
       手配タスク（子）  … 作業・ステータス・期限・通知の単位
```

### 2.2 各層の役割

| 層 | 役割 |
|---|---|
| **起票（親）** | 依頼の受付単位。起票者、依頼日、現地使用日などを持つ |
| **部材群** | 起票時の入力単位。群ごとに入力方式（フォーム/Excel貼付）を選ぶ |
| **明細** | 部材1点＋数量。所属する手配タスクは常に1つ |
| **手配タスク（子）** | 作業の単位。ステータス・担当者・期限・通知はすべてここに付く |

### 2.3 部材群と手配タスクの関係

- **1つの部材群から複数の手配タスクが生まれる**（1対多）
- 明細層を挟むことで、手配タスクが複数の部材群の明細を抱えても構造は壊れない
- **部材群をまたぐ融合を禁止する制約は設けない**（制約のほうが実装が増え、将来の正当なケースを塞ぐため）

### 2.4 起票者列に関する注記

フロー経由で作成された行は、SharePointの `登録者` 列が**フローの接続作成者**になり、
実際に起票した人にはならない（`docs/環境台帳.md` §「コネクタの認証方式」参照）。

→ **実際の起票者を保持する列を別途持つこと。** `登録者` 列は監査用の副次情報として扱い、
業務上の起票者はこの専用列を正とする。

## 3. 起票

### 3.1 入力方式

部材群ごとに、以下のいずれかを選択して入力する。

**① フォーム形式**
選択式で部材と数量を入力する。フォーマットが存在しない部材群はこちらを使う。

**② Excel貼り付け**
部材必要数をまとめたExcelフォーマットから、範囲コピーして貼り付ける。

- フォーマットは特定の分類の部材群ごとに存在する（存在しないものもある）
- 同一部材群で**2パターン存在する可能性がある**
- 部材の並び順は決まっており、**横長または縦長のベクトル**で数量が記載される

### 3.2 複合起票

1回の起票で複数の部材群を扱う。**群ごとに①か②を選択できる。**

### 3.3 Excel貼り付けの実装方針

- Excelの範囲コピーは、クリップボード上で**タブ区切り＋改行**のテキストになる
- テキストエリアで受け取り、ブラウザ内で解析する（外部ライブラリ不要）
- **縦長／横長は転置処理で両対応**。自動判定を試み、外れた場合は人が選び直せる
- 2パターンは貼り付け内容から自動推定し、外れた場合は人が選び直せる

### 3.4 起票UIの位置づけ

- **SharePointの標準フォームでは実現できない。自作の単一HTML画面とする**
- 会社環境に依存しないため、**自宅で完全に作り込める**

## 4. ステータスと業務フロー

### 4.1 標準の流れ

**親レベル**

1. 起票者記票（担当者割り当てを含む）
2. 行自動振り分け確認・手動修正（起票者・担当者）

**子（手配タスク）レベル**

3. 発注ノウハウ確認
4. 見積取得
5. 発注
6. システム処理・上司承認
7. 発注完了確認
8. 納品確認
9. 検収確認

### 4.2 段階の可変性

- 段階は**ほぼ共通**だが、手配方法によって**スキップまたは大幅に変わる**場合がある
- **業務整理は未完了。整理が進むことを前提とした設計にする**
- ステータスの流れを実装に埋め込まず、**手配方法マスタに持たせる**
  → 整理が進むたびにマスタへ行を足すだけで済み、ツール本体の作り直しが発生しない
- 最初は数種類だけマスタに登録して運用を開始し、育てていく

### 4.3 検収の自動クローズ

- 検収確認は重要度が低い
- **未完了でも2か月経過したらタスク終了とする**
- 日次のスケジュール処理で実現する
- **自動クローズされた事実がわかるフラグを残す**（後の監査のため）

## 5. 自動振り分け

### 5.1 判定方法

- **部材の分類コードや品目名から機械的に決まる**
- **約9割は自動判定可能**
- 残り1割は特殊要素があり人が判断する → **v1では対象外**

### 5.2 人による確認

- 自動振り分けの結果は、**ステータス2で起票者・担当者が確認し、手動修正できる**
- 自動判定の例外はこのステップで吸収される

## 6. 手配方法マスタ

本ツールの中核。以下を保持する。

| 項目 | 内容 |
|---|---|
| 手配方法コード | 識別子 |
| 判定条件 | この分類コード／品目名なら、この手配方法 |
| 使う段階 | 標準9段階のうちどれを通るか、スキップするか |
| 各段階のリードタイム | 逆算に使用 |
| ノウハウ集へのリンク | 次フェーズで定義 |

**マスタの中身（実際の分類コード、手配方法名、社内の承認ルール）は業務固有情報のため、リポジトリには載せない。** 構造のみリポジトリで管理し、中身は会社側で埋める（`PROJECT.md` §4 参照）。

## 7. 期限管理

### 7.1 管理する期限

1. 部材の納期（届く日）
2. 依頼への回答・承認期限
3. **現地で使う日（逆算の基準）**
4. 発注手続きの締切

### 7.2 逆算

**現地使用日を起点に、手配方法マスタのリードタイムで各段階の「必要な作業日」を算出する。**

```
現地使用日 → 納期 → 発注締切 → 承認期限
```

この「必要な作業日」が、遅延通知の判定基準となる。

## 8. 通知

### 8.1 基本原則

**順調なら黙る、遅れたら鳴る。**
担当者の能動的な作業が終わった時点（納品待ち）で、その担当者への通知は止める。

### 8.2 通知一覧

| # | 発火条件 | 宛先 | 回数 |
|---|---|---|---|
| 1 | 担当者に割り当てられた | 新担当者 | 1回 |
| 2 | 担当者が変更された | 新担当者 | 1回 |
| 3 | 納品待ちに到達した | 担当者 | 1回（担当者への最後の通知） |
| 4 | 各作業締め日までに未着手 | 担当者 | **締め日ごとに複数回** |
| 5 | 納品確認 | **起票者** | 1回 |

### 8.3 融合時の通知

融合により担当を失った旧担当者へ、**「担当分がタスクXに統合されました」を1回だけ通知する**。

### 8.4 メンション実装上の注意

- Teamsで本物のメンション（通知が飛ぶ形）にするには、**メールアドレス等のユーザー識別子が必要**
- 本文に `@氏名` と文字列で書いても平文表示になり、通知は飛ばない
- 台帳の担当者列は Person型（SharePointリストの場合）またはメールアドレスで保持する

## 9. 融合・分割

### 9.1 融合の条件

- **手配方法が同じもの同士のみ**（段階もリードタイムも異なるとステータスが破綻するため）
- **両方が発注前の段階にあること**（発注済みとの融合は不可）
- 部材群をまたぐことは**許可する**（制約を設けない）

**注**: このガードは自作UI側で効かせるものであり、台帳を直接編集された場合は素通りする。v1では割り切る。

### 9.2 項目の扱い

融合時、項目の性質によって扱いを分ける。

| 性質 | 例 | 扱い |
|---|---|---|
| **合算** | 数量、金額 | 足す |
| **選択** | 手配方法、担当者、備考 | どちらかを選ぶ |
| **推奨つき選択** | 期限 | **早いほうを推奨。ユーザーによる変更は可能** |
| **連結** | 備考、参照リンク | 両方残す |

### 9.3 期限変更時の扱い

- 推奨（早いほう）から変更した場合、**画面に警告を表示する**
- **推奨から変更した事実を台帳に記録する**（後で判断の意図が追えるように）

### 9.4 選択UIの方針

**値が食い違う項目のみ提示し、一致する項目は自動確定する。** 差分だけを人に聞く。

### 9.5 消える側の扱い

物理削除せず、**「融合済み」ステータスで残し、統合先のIDを保持する**。
履歴と通知ログを壊さないため。

### 9.6 逆操作

- **v1では「融合直後の取り消し」のみ実装する**
- 任意タイミングでの分割・再分割はv2以降
- ただし振り分け結果の手動修正（ステータス2）で分割操作は既に必要なため、機能としては地続き

## 10. 削除の扱い

### 10.1 方針

**物理削除は行わない。論理削除とする。**

- 台帳に「削除フラグ」列を持ち、既定ビューでは非表示にする
- フラグを立てられるのは**起票者のみ**（ツール側で制御）

### 10.2 理由

- 台帳という性質上、行が消えるべきではない（誤操作、監査）
- SharePointの標準機能では「起票者だけが削除できる」を実現できない
  → アイテムレベル権限を使うと「自分の行しか編集できない」も同時にかかり、
    担当者が他人の行を更新できなくなるため、業務フローと衝突する

### 10.3 権限設定（SharePointリストを採用する場合）

- Contribute をコピーしたカスタム権限レベルを作り、**Delete Items を外す**
- **適用範囲はリストのみに絞る**
  （Delete Items を外すとファイル名変更ができなくなる仕様があり、
   ドキュメントライブラリに適用すると副作用が出る）
- **カスタム権限レベルの作成にはサイト権限の管理権限が必要。会社環境での確認が必要**

## 11. メンテナンス機能

### 11.1 位置づけ

マスタ編集画面の**共通基盤**として設計する。今後増える前提。

### 11.2 現時点で必要なマスタ

| マスタ | 中身 |
|---|---|
| **部材フォーマット定義** | 部材群ごとの並び順、縦横、パターン |
| **手配方法** | 判定条件、通る段階、リードタイム、ノウハウリンク |
| **担当者** | 氏名とメールアドレスの対応。**必須**（Person型はテキストの自由入力を受け付けず、ディレクトリに実在するユーザーしか設定できないため。`docs/環境台帳.md` §B-3） |

### 11.3 設計方針

**すべて同じ形（一覧 → 編集 → 保存）に統一する。** 4つ目5つ目が増えても作り足すだけで済む形にする。

## 12. 会社環境への追加確認事項

`PROJECT.md` §7 に加えて、本書の内容から以下が必要になった。

- SharePointの**カスタム権限レベルを作成できる権限**があるか
- 担当者を **Person型列**で持てるか（Teamsメンションに必要な識別子が取得できるか）
- **アダプティブカードのフォーム送信**を台帳に書き戻せるか
  （Yes/Noの承認だけでなく、値の入力まで必要なため）
- マスタ・フォーマット定義の**永続化先**をどこにするか
