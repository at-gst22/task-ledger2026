## 1. スコープ

### 1.1 本書で定義するもの

台帳のデータ構造 / 起票 / ノウハウ集 / マスタ群 / ステータスと業務フロー /
期限管理と逆算 / 通知 / 融合・分割 / 削除 / メンテナンス機能 / バージョン管理

### 1.2 未定義

- ノウハウ集の**中身**（手順そのもの）は、運用しながら整備していく
- 手配方法ごとの具体的なステップ、リードタイム、判定条件

### 1.3 実現方式（環境調査で確定）

- **台帳は SharePointリスト**
- **Boxは成果物ファイルの格納先、および各HTMLツールの配布先**
- 通知・双方向連携は Power Automate の標準コネクタで実現可能
- **起票UIからの直接書き込みは不可**（プレミアム必須）→ §3.10 のファイル方式で代替
- **グリッドビューへの貼り付けは不採用**（`環境台帳.md` §X）

### 1.4 成果物の構成

| ファイル | 役割 | 配布 |
|---|---|---|
| **起票UI** (HTML) | 起票、明細作成、分割、JSON出力 | Box。**バージョン厳格管理**（§7） |
| **ノウハウ集** (HTML) | 手順の参照、メール生成、ノウハウ投稿 | Box。**気軽に更新** |
| **メンテナンス** (HTML) | 全マスタの編集と、上記2ファイルの生成 | Box。管理者のみ |

**起票UIとノウハウ集を分離する理由**

- 更新頻度が違う。ノウハウ集は運用しながら頻繁に更新するが、
  起票UIはバージョン管理下にあり、更新のたびに許可バージョンの登録が必要になる
- 読む人が違う。ノウハウ集は起票しない担当者も参照する

## 2. データ構造

### 2.1 3層構造

```
起票（親）              … 部材群1つ分の依頼。1起票＝1部材群
 └ 明細                 … 部材1点＋数量。数量データの実体
     ↓ 手配方法でグルーピング
    手配タスク（子）     … 作業・ステータス・期限・通知の単位
```

**部材群は独立した層ではなく、起票の属性である。**
複数の部材群を扱う場合は、起票を複数件作る（§3.2）。

### 2.2 各層の役割

| 層 | 役割 |
|---|---|
| **起票（親）** | 部材群、納入先、納品日、起票者、既定担当者、前提条件の確認記録 |
| **明細** | 部材1点＋数量。所属する手配タスクは常に1つ |
| **手配タスク（子）** | 作業の単位。ステータス・担当者・期限・通知はすべてここに付く |

### 2.3 明細と手配タスクの関係

- **1つの起票から複数の手配タスクが生まれる**（1対多）
- 明細層を挟むことで、手配タスクが複数の起票の明細を抱えても構造は壊れない
- **起票をまたぐ融合を禁止する制約は設けない**

### 2.4 起票者の保持（重要）

SharePointの `登録者` 列は、**フロー経由で作成された行では「接続作成者」になる**
（`環境台帳.md` §C-5）。

したがって、**実際の起票者を保持する列を別途持つこと。**
`登録者` を起票者として扱ってはならない。

### 2.5 起票ID

**各起票にUUIDを付与する。** 重複取り込みの防止に使う（§3.11）。

親リストの起票ID列には**一意制約を設定する**。
設定可能であることを確認済み（`環境台帳.md` §B-2）。

## 3. 起票

### 3.1 起票の単位

**1起票 ＝ 部材群1つ。**

### 3.2 セッション（複数起票）

1回の作業で複数の起票を作成できる。これは**UIの機能であり、データ構造ではない**。

- 起票を追加すると、**直前の起票から属性を転記できる**
  （納入先 / 納品日 / 起票者 / 既定担当者）
- 転記した内容は個別に手入力・修正できる

### 3.3 入力の流れ

```
1. 部材群を選択          ← 必ずユーザーが選ぶ
     └ 前提条件を表示し、確認チェックを取る（§3.8.2）
2. フォーマットを選択      ← 候補提示はするが、確定はユーザー
3. 数量を入力
     ├ Excelから貼り付け（フォーマットがある場合）
     └ UI上で選択・修正（フォーマットが無い／貼付後の修正）
4. 起票の属性を入力（§3.8）
5. 確認 → 次の起票へ、または送信
```

**貼り付けとUI編集は排他ではない。**
貼り付けた結果がそのまま編集可能な明細一覧となり、追加・削除・数量修正ができる。

### 3.4 Excelフォーマットの構造（実物の観察結果）

- **品目は一方向に並び、数量はそれと直交する方向に並ぶ**
  - 行ベクトル形式 / 列ベクトル形式
- **同一の部材群に、複数のバリアントが存在する**
  - 例: 社内用と社外用。**並び順が異なり、載っている部材にも差がある**
  - **形状が異なる場合がある**
- 結合セル、セル内改行、数式エラー、セルコメントが混在する
- **貼り付けるのは数量の並びのみ**

### 3.5 貼り付けデータの解釈

**貼り付けたデータには、部材を示す情報が一切含まれない。** 位置だけが手がかりとなる。

```
貼り付けた値の位置（N番目）
  ↓ フォーマット定義（§6.2）
内部コード
  ↓ 部材マスタ（§6.1）
分類コード
  ↓ 手配方法マスタ（§6.3）
手配方法 → 通る段階 / リードタイム / ノウハウ集の該当手順
```

### 3.6 位置合わせのリスクと対策

**並びが1つずれると全明細が誤り、しかも静かに誤る。**

**① 選択は必ずユーザーが行う** — 形状と要素数から候補を提示するが、確定はユーザー
**② 要素数の検証** — 期待要素数と照合し、不一致なら警告して保留
**③ 取り込み結果の目視確認** — 「N番目 ＝ 品名 ＝ 数量」で一覧表示

### 3.7 値の扱い

| 値 | 扱い |
|---|---|
| `0` / 空欄 | **不要とみなし、明細を作らない** |
| 数式エラー / 数値以外 | **スキップし、警告を表示**。取り込みは止めない |

### 3.8 起票の属性

| 項目 | 形式 | 備考 |
|---|---|---|
| 納入先情報 | **複数行の自由記述テキスト1つ** | §3.8.1 |
| 納品日 | 日付 | 「未定」可 |
| 起票者 | 担当者マスタから選択 | 「未定」可 |
| 既定担当者 | 担当者マスタから選択 | 「未定」可 |
| **前提条件の確認** | チェック＋確認者・日時 | §3.8.2 |

**すべて「未定」を明示的に選択できる。** 空欄（入れ忘れ）と未定（意図的）を区別するため。
**必須チェックは行わない。**

#### 3.8.1 納入先情報を構造化しない理由

各種のフォーマットが既にテキスト形式で存在しており、**貼り付けるだけで済む形が最も速い**。
項目ごとに分割させると、貼ったテキストを手で切り分ける作業が発生する。

代わりに、薄字のプレースホルダとガイドラインで「何を書くべきか」を伝える。
**ガイドラインの文面はマスタで管理し、部材群ごとに切り替える**（§6.5）。

#### 3.8.2 前提条件の確認

手配方法によっては、**本ツールのスコープ外の作業の完了を契機として着手する**ものがある。
システムは完了を判定できないため、**確認を促し、確認した事実を記録する**。

- 部材群を選んだ時点で、前提条件の文面を表示する（§6.3）
- **確認チェックを取り、確認者と日時を起票の列として保持する**
- チェックは必須にしない。未確認のまま進めることもできる（記録には残る）
- 同じ文面をノウハウ集の手順冒頭にも表示する

### 3.9 分割ロジック

#### 3.9.1 基本規則

**同じ手配方法の明細を1つの手配タスクにまとめる。**

```
手配タスク ＝ 起票 × 手配方法
```

**理由**: §10.1 で融合の条件を「手配方法が同じもの同士のみ」と定めた。
この分割は**最初から融合済みの状態で作る**ことと等価であり、分割と融合の粒度が一致する。

#### 3.9.2 担当者の決まり方

```
起票時      … 起票全体の既定担当者を1人指定（未定も可）
分割後      … 全タスクにその担当者を継承
ステータス2 … タスクごとに担当者を修正
```

#### 3.9.3 分割の実行場所

**起票UI（ローカルHTML）の中で分割まで完了させる。**
起票UIが親・明細・タスクの3種類を含むJSONを生成する。

そのため**起票UIは部材マスタと手配方法マスタを保持する**（§3.13）。

#### 3.9.4 例外の吸収

同じ手配方法でも分けたい場合は、ステータス2の確認画面で**手動分割**する。

### 3.10 台帳への送信方式

**ファイル方式に一本化する。**

起票UIから SharePoint へ直接書き込むことはできない
（「HTTP要求の受信時」トリガーがプレミアムのため）。

#### 3.10.1 基本の流れ

```
起票UI → JSONファイル（親・明細・タスクを1件にまとめる）
   ↓ 人が配置
［起票受付ライブラリ］（SharePointドキュメントライブラリ）
   ↓ トリガー発火（標準）
Power Automate
   ↓ SharePoint に HTTP 要求を送信します（標準）
［親リスト］［明細リスト］［タスクリスト］
```

- **ファイル名は起票UI側で一意に生成する**
  （例: `kihyou_YYYYMMDD_HHMMSS_<短縮ID>.json`）
- ライブラリへの配置は**ドラッグ＆ドロップ**で行う（数秒）
- 取り込み後、ファイルは状態別フォルダへ移動する
  - `取込済` / `重複スキップ` / `エラー`
  - **取り込まなかった場合も必ず移動させる**（受付フォルダに残るものが未処理）

#### 3.10.2 即時反映

自動トリガーはポーリングのため**数分のラグがある**。
急ぐ場合は、**ライブラリ上でファイルを選択し、手動でフローを実行する**。

```
ライブラリでファイルを選択
 → [統合] → [フロー] → 対象のフロー
 → 数秒で台帳へ反映
```

`選択したファイルの場合` トリガーが標準で利用可能であることを確認済み
（`環境台帳.md` §C-1, §D-2）。

**注意**: ファイルを選択していない状態では、メニューに「使用可能なフローはありません」
と表示される。**必ずファイルを選択してから開く**。

#### 3.10.3 グリッドビューへの貼り付けを採用しない理由

検証の結果、**実用に耐えないことが判明した**（`環境台帳.md` §X）。

- **Person型列に貼り付けると、ブラウザが応答不能になる**（2台のPCで再現）
- 担当者は必ずPerson型で持つ設計であり（Teamsメンションに必須）、
  その列に貼り付けられないなら方式として成立しない
- 一部のPCでのみ固まる機能を、全員配布のツールの導線に置けない

即時性は §3.10.2 の手動実行で確保できるため、廃止による損失はない。

**副次的な利点**

- 3リストへ順序どおり貼るという**間違えやすい操作が消える**
- Person型の解決は**サーバ側**で行われるため、ブラウザは固まらない
- **PCの性能に依存しない**
- 重複防止を起票IDで一元化できる

### 3.11 重複取り込みの防止

#### 3.11.1 フローによる判定

フローが起票IDを確認し、**既に台帳に存在すれば取り込まない**。
ファイルは `重複スキップ` フォルダへ移動する。

#### 3.11.2 一意制約による防止

親リストの起票ID列に **「固有の値を適用する」** を設定する。
重複した行は**物理的に登録できなくなる**。

**設定時の注意**: 「この列にインデックスを付けますか？」というダイアログが出る。
**OKで進んでよい**（`環境台帳.md` §B-2）。

#### 3.11.3 起票IDの持たせ方

| リスト | 起票ID | 一意制約 |
|---|---|---|
| 親 | 1行に1つ | **あり**（門番） |
| 明細 / タスク | 同じIDが複数行 | なし |

親を守れば全体が守れる。

### 3.12 送信画面のUI要件

- **JSONファイルの保存先**と、その後の操作を明示する
- ライブラリへの配置方法（ドラッグ＆ドロップ）を案内する
- 自動取り込みには**数分のラグがある**旨を表示する
- 急ぐ場合の**手動フロー実行の手順**を表示する
  （ファイルを選択してから [統合] → [フロー] を開くこと）
- **送信完了後、生成された手配タスクごとに「この手順を見る」導線を出す**（§4.7）

**案内文の文面はマスタで管理する**（§6.5）。
実際のメニュー名やパスが想定と異なる場合、会社側で修正できるようにするため。

### 3.13 起票UIの実装方針

#### 3.13.1 形態

- **自作の単一HTML**。SharePointの標準フォームでは実現できない
- **ローカルHTMLの動作とクリップボード解析の成立を確認済み**（`環境台帳.md` §E）
- 外部ライブラリを使わず、ブラウザ内で完結
- 行ベクトル／列ベクトルは転置処理で両対応

#### 3.13.2 マスタの保持方法

**マスタはHTMLに埋め込む。外部JSONファイルの読み込み方式は採用しない。**

**理由**: 外部ファイルが必要なことを理解していない利用者がいるため、
**ファイル単体で動作しない仕組みは採用できない**。

**マスタのローカル編集機能は設けない。**
各利用者のマスタが分岐し、バージョン管理と衝突するため。

#### 3.13.3 配布

**Boxに配置する。** 差し替えれば、全員が次に開いたときに新版となる。

**Box Drive 経由でローカルファイルとして開く。**
動作を確認済み（`環境台帳.md` §E）。

## 4. ノウハウ集

### 4.1 位置づけ

**作業のすべての入口。「困ったらここを開く」を1箇所に定める。**

手配手順の参照が主目的だが、**起票のしかたも含める**（§4.8）。

### 4.2 形態と制約

**別の単一HTML。Boxに配置する。**

**SharePointとの連携はできない。** ローカルで開いたHTMLは認証できないため、
台帳を読むことも、台帳から呼び出されることもできない。

したがって、**利用者が手配方法を自分で選ぶ**形とする。

```
［手配方法を選択］ ▼
［今どの段階か］   ▼  ← 任意。選べば該当ステップから始まる
     ↓
現在のステップを表示
```

**一方、HTMLから外へ出ていく操作は問題なく動作する**（検証済み）。

- SharePoint / Box のURLを開く
- `mailto:` でOutlookを起動する
- Microsoft Forms を開く
- 同一フォルダの別HTMLへ、URLパラメータ付きで遷移する

本章の機能はすべてこの「外へ出る」側であり、制約の影響を受けない。

### 4.3 手順ステップの構造

**手順を部品化し、手配方法はその並びを指す。**

手配方法ごとに手順書を書くと、共通部分が重複し、修正時に全箇所を直すことになる。
「部分的に同一の手順がある」という実態に対して、**共通ステップを1つ書いて複数から参照する**。

```
手順ステップマスタ
├ ステップID
├ タイトル
├ 説明（何をするか）
├ リンク（ツール／Boxフォルダ）＋そこでの作業内容
├ メール定型ID（該当する場合。§4.5）
├ 所属ステータス（9段階のどれか）
└ 次のステップ（条件つきで複数持てる）
```

### 4.4 分岐ナビゲーション（ゲームブック形式）

**画面には、現在のステップと、そこから進める選択肢だけを表示する。**

手配プロセスが多く、部材群ごとに手順が異なるため、
全手順を一覧表示すると「どこを読めばよいか分からない」状態になる。

- 現在のステップの内容を表示
- 「次はどれか」を選択肢として提示（条件つき分岐）
- 前のステップへ戻れること
- 全体の流れを俯瞰する表示も用意する（現在地が分かる形）

### 4.5 メール定型（Outlook連携）

手順の中に、**所定の宛先へメールを送る**ステップがある（現時点で3ステップ程度）。

```
メール定型マスタ
├ 定型ID
├ 宛先 / CC
├ 件名（差し込み可）
└ 本文（差し込み可）
```

**`mailto:` リンクで実現する。動作を確認済み**（`環境台帳.md` §F）。

- 件名の日本語、本文の改行、記号のいずれも正常
- 差し込み値（品名・数量・納期）も正常
- **送信ボタンは人が押す**ため、誤送信の懸念がない

**制約**
- 本文の長さに上限がある（URLとして渡すため。数千文字程度が実用上の限界）
- **書式なしテキストのみ**（太字・表は不可）
- **添付ファイルは付けられない**

現在想定している定型は「文面フォーマットが決まっており、宛先・数量・納期を差し込む」
という形のため、上記の制約には抵触しない。

#### 4.5.1 既定のメールアプリ

環境に **Outlook (classic)** と **新しい Outlook** が併存する。
検証は classic で実施した。**新しいOutlookでの挙動は未検証。**

§4.8 の「環境の準備」に、既定アプリの設定手順を記載する
（手順は `環境台帳.md` §F-1）。

### 4.6 前提条件の表示

手順の冒頭に、その手配方法の前提条件をチェックリストとして表示する（§3.8.2）。
文面は手配方法マスタが持つ（§6.3）。

### 4.7 起票UIからの導線

**起票の送信完了画面から、生成された手配タスクごとに該当手順を開く。**

起票時点で手配方法は自動振り分け済みのため、**該当手順を開いた状態で起動できる**。

```
送信完了
├ 手配タスク1（手配方法α） → [このタスクの手順を見る]
├ 手配タスク2（手配方法β） → [このタスクの手順を見る]
└ 手配タスク3（手配方法γ） → [このタスクの手順を見る]
```

同一フォルダに配置し、相対リンク＋URLパラメータで手配方法を渡す。
**日本語パラメータを含めて動作を確認済み**（`環境台帳.md` §E）。

**Teams通知からのリンクは行わない。** ローカルファイルへのリンクはTeamsから開けないため、
通知には「ノウハウ集で手配方法◯◯を確認してください」と文言で案内する。

### 4.8 §0「はじめに」

**手配方法に依存しない共通部として、ノウハウ集の先頭に置く。**

```
0. はじめに
   ├ 0-1. 環境の準備
   │   ├ Outlookの既定アプリ設定（メール生成機能を使う場合。初回のみ）
   │   └ Teamsのチャネル通知設定（§4.8.1）
   ├ 0-2. 起票のしかた
   │   ├ ツールを開く
   │   ├ 部材群を選ぶ（前提条件の確認）
   │   ├ 数量を入力する（貼り付け／手入力）
   │   └ 属性を入力する
   └ 0-3. 台帳への送り方
       ├ JSONファイルを保存する
       ├ ライブラリへ配置する
       └ 急ぐ場合の手動実行
```

**0-1 は初回のみ必要なため、既定で折りたたむ。**

**理由**
- 利用者は起票UIの使い方を知らない。ツールの説明がどこにも無い状態を避ける
- ノウハウ集を作業のすべての入口とするため

起票UIの中からもここへリンクする。

#### 4.8.1 Teamsのチャネル通知設定

通知はチャネルへ投稿する（§9.7）。他人宛ての通知で埋もれないよう、
**チャネルの通知を絞り、自分がメンションされたときだけ気づく**設定を案内する。

**要点: 個人宛てのメンション（@自分）は、以下の設定に関わらず必ず通知される。**

**チャネル単位の設定**

```
チャネル名の横の […] → チャネルの通知
├ すべての新しい投稿      → オフ
└ チャネルでのメンション  → オン（任意）
```

**新しく参加するチャネルの既定値**

```
設定 → 通知とアクティビティ
└ チャネルの既定動作を設定する
```

**記載上の注意**

- 会社環境のTeamsのバージョンによってメニュー名が異なる可能性がある
- **スクリーンショットは §4.11 のプレースホルダ規約で用意し、会社側で挿入する**
- 手順の文言そのものも、実際の画面に合わせて会社側で修正できるようにする

### 4.9 ノウハウ投稿

**主目的を邪魔せず、気づいたときに蓄積できる導線を用意する。**

Microsoft Forms の**事前入力パラメータ**を使う。

```
手順ステップの画面
 └ [気づいたことを送る] クリック
      ↓
 ブラウザでFormsが開く
 ├ 手配方法: ◯◯   ← URLパラメータで自動入力
 ├ ステップ: 手順5  ← 同上
 └ 気づいたこと: __ ← ここだけ書く
      ↓ 送信
 Power Automate（Formsトリガー・標準）
      ↓
 SharePointの「ノウハウ投稿」リスト
      ↓
 管理者が採否を判断 → 次版のノウハウ集へ反映
```

**設計の要点**

- **書くのは1項目だけ。**「どの手順の話か」は自動で付く
  （自由記述だけだと、何の話か分からない投稿が溜まる）
- **投稿は即座には反映されない。** 誰でも直接書き換えられると手順書の信頼性が崩れる

**事前入力済みURLの取得**（`環境台帳.md` §G）

- Forms編集画面の […] メニューに **「事前入力済み URL の取得」** がある
- 質問の内部IDを手で調べる必要はない
- **必ず正式形のURLを使う。**短縮形（`/r/XXXXXX`）では転送時にパラメータが消える
- 取得したURLは**マスタに登録し**、ツール側はダミー値を実際の値へ置換するだけとする
  → 設計側が内部IDを知らなくても成立し、質問の増減にも追従できる

### 4.10 注意点・落とし穴の集積は行わない

煩雑になるため、独立した項目としては設けない。
必要な注意事項は該当する手順ステップの説明に直接書き込む。
運用の中で §4.9 の投稿から拾い上げる。

### 4.11 スクリーンショットの扱い

会社環境の画面はリポジトリに含められない（`PROJECT.md` §4）。
**HTMLにはプレースホルダのみを置き、画像は会社側で挿入する。**

**記法**

```html
<!-- SCREENSHOT: 何を撮るべきかをここに書く -->
<figure class="shot" data-shot="識別子">
  <img src="img/識別子.png" alt="説明">
  <figcaption>キャプション</figcaption>
</figure>
```

- 画像が無くても**表示は崩れない**（alt文字が出るだけ）
- `data-shot` により、**未挿入のスクリーンショットを機械的に一覧化できる**
- 管理者向けの点検ページで、未挿入の一覧を表示する
- 画像は `img/` に配置し、**会社側でのみ管理する**
- **`img/` は `.gitignore` に含める。**ノウハウ集を差し替えても上書きしない運用とする

## 5. ステータスと業務フロー

### 5.1 標準の流れ

**親レベル**

1. 起票者記票（既定担当者の指定を含む）
2. 行自動振り分け確認・手動修正（起票者・担当者）

**子（手配タスク）レベル**

3. 発注ノウハウ確認
4. 見積取得
5. 発注
6. システム処理・上司承認
7. 発注完了確認
8. 納品確認
9. 検収確認

### 5.2 段階の可変性

- 段階は**ほぼ共通**だが、手配方法によって**スキップまたは大幅に変わる**場合がある
- **業務整理は未完了。整理が進むことを前提とした設計にする**
- ステータスの流れを実装に埋め込まず、**手配方法マスタに持たせる**

### 5.3 ステータス3「発注ノウハウ確認」

**ノウハウ集の該当手順を開いて確認する。記録は残さない。**

完了操作は、**Teams通知のアダプティブカードから行う**（§5.5）。
慣れた担当者にとって負荷が最小になる。

不要な手配方法ではこの段階自体をスキップできる（§5.2）。

### 5.4 検収の自動クローズ

- **未完了でも2か月経過したらタスク終了とする**
- 日次のスケジュール処理で実現する（標準で利用可）
- **自動クローズされた事実がわかるフラグを残す**

### 5.5 Teamsからのステータス更新

**ステータスの更新は、SharePointを開かずに Teams から行える。**

```
通知が届く（例: 担当者に割り当てられました）
 └ カード内で操作
      ├ ステータス      … 選択肢
      ├ 日付            … 日付ピッカー
      └ コメント        … 自由記述
      ↓ 送信
    台帳が更新される
```

**動作を確認済み**（`環境台帳.md` §C-2）。

- 「アダプティブ カードを投稿して応答を待機する」は標準
- **選択肢・日付・自由記述の3種類とも表示され、値が正しく返る**（日本語を含む）
- 応答には `messageLink` も含まれるため、**台帳の行から該当の通知へリンクを張れる**
  → 後から経緯を追えるようにする用途に使う

### 5.6 応答者の検証

通知はチャネルへ投稿するため（§9.7）、**担当者以外もカードを操作できる**。
誤操作を防ぐため、フロー側で応答者を検証する。

```
応答を受け取る
  ↓
応答者のメールアドレス ＝ 当該タスクの担当者か？
  ├ 一致   → 通常どおり更新
  └ 不一致 → 別処理（§5.6.2）
```

#### 5.6.1 前提の確認（未検証）

**カードの応答に、応答者を識別できる情報が含まれるか**は未確認。
実行履歴の出力を全項目確認することで判明する（`環境台帳.md` 未確認事項）。

含まれない場合は、カードの操作を担当者に限定できないため、
**カードによる通知を個人チャットへ切り替えるか、検証を諦めるか**を選ぶことになる。

#### 5.6.2 不一致だった場合の処理（未定）

以下の案がある。**運用を見てから決める。**

| 案 | 内容 |
|---|---|
| 拒否 | 台帳を更新せず、応答者へ「担当者ではありません」と返す |
| 警告つき更新 | 更新はするが、応答者と担当者の双方へ注意を通知する |
| **代理操作として記録** | 更新し、「誰が代理で操作したか」を台帳に残したうえで担当者へ通知する |

**3案目が実務に合う可能性がある。**
急ぎの場面で他者が代わりに操作する、という運用は起こりやすいため。

### 5.7 テキスト返信によるステータス更新（v2以降の候補）

カードを押さず、**スレッドへの返信で更新できる**と、
スマートフォンからの操作などで利便性が上がる。

**実現方法**

```
カード投稿 → messageLink をタスク行に保存
                ↓
「チャネルに新しいメッセージが追加されたとき」トリガー（標準）で返信を検知
                ↓
スレッドを突き合わせて該当タスクを特定
                ↓
本文を解釈してステータスを更新
```

**未検証の点**

1. 上記トリガーが**スレッド返信で発火するか**（新規投稿のみ拾う可能性がある）
2. `messageLink` から返信スレッドを特定できるか

**本文の解釈は、厳密な合図に限定する。**

```
!done       → 次のステータスへ
!hold       → 保留
!date 9/23  → 納期変更
```

自然文の解釈は行わない。「完了」「済み」「OK」「おわりました」など表記の揺れが
無限にあり、誤判定と誤爆の温床になるため。

**位置づけ**: カード操作を主、テキスト返信を補助とする。
テキスト返信が有効な場面は頻度が低いと見込まれるため、主導線にはしない。

## 6. マスタ群

**中身は業務固有情報のため、リポジトリには載せない。**
構造のみリポジトリで管理し、中身は会社側で登録する（`PROJECT.md` §4）。

### 6.1 部材マスタ

| 項目 | 内容 |
|---|---|
| **内部コード** | **システムが振る一意のキー。不変。意味を持たせない** |
| 品番 | 社内の品番。**空欄可**。表記ゆれ・重複はここで吸収する |
| 品名 | 表示名 |
| 分類コード | 手配方法の自動振り分けに使う |

**社内品番をキーにしない**（表記ゆれと重複があり、明細の紐づけが破綻するため）。
**仮コードのフラグは持たない**（品番が空欄であれば未確定と分かるため）。

### 6.2 フォーマット定義

**部材群 × バリアント**の単位で持つ。

| 項目 | 内容 |
|---|---|
| フォーマットID / 部材群 / バリアント名 | |
| 形状 | 行ベクトル / 列ベクトル |
| 期待要素数 | 検証に使う |
| 並び | **N番目 → 内部コード** の対応表 |

### 6.3 手配方法マスタ

| 項目 | 内容 |
|---|---|
| 手配方法コード | 識別子 |
| 判定条件 | この分類コードなら、この手配方法 |
| 使う段階 | 標準9段階のうちどれを通るか、スキップするか |
| 各段階のリードタイム | 逆算に使用 |
| **前提条件** | スコープ外の契機。文面と確認方法（§3.8.2） |
| **開始ステップID** | ノウハウ集の手順の入口（§4.3） |

### 6.4 担当者マスタ

**必須。** Person型列はディレクトリに実在するユーザーしか設定できず、
テキストでの自由入力ができないため（`環境台帳.md` §B-1）。

| 項目 | 内容 |
|---|---|
| 氏名 / メールアドレス | Person型列への設定、Teamsメンションに使用 |

起票UIでは担当者を**選択式**とし、このマスタから選ばせる。

### 6.5 文面マスタ

UIに表示する案内文を保持する。実装に埋め込まない。

| 用途 | 内容 |
|---|---|
| 納入先ガイドライン | 部材群ごとに切り替え可能 |
| 納入先プレースホルダ | 薄字で表示する記入例 |
| 送信手順の案内 | ライブラリへの配置方法、手動フロー実行の手順 |
| ノウハウ投稿URL | 事前入力済みURLのひな型（§4.9） |

**理由**: 実際のメニュー名・パス・記載ルールが想定と異なる場合、
会社側で修正できるようにするため。

### 6.6 手順ステップマスタ

§4.3 の構造。ノウハウ集が保持する。

### 6.7 メール定型マスタ

§4.5 の構造。ノウハウ集が保持する。

### 6.8 許可バージョンマスタ（SharePoint側）

**このマスタのみ、SharePointリストとして持つ。**

| 項目 | 内容 |
|---|---|
| バージョン / 状態（許可・非許可）/ 備考 | |

検証フローがこれを参照する（§7.2）。
新版を配布したらこのリストに1行追加するだけでよく、ツール側の改修は不要。

## 7. バージョン管理

### 7.1 識別子

**起票UIが出力するJSON**に識別子を埋め込む。

```
形式例: TLV|<バージョン>|<出力日時>|<マスタのハッシュ>
```

### 7.2 検証

**フローが取り込み前に検証し、不正なバージョンなら取り込まない。**
ファイルは `エラー` フォルダへ移動し、起票者へ通知する。

貼り付け方式を廃止したため、**検証はフロー側で完結する**。
台帳へ直接書き込まれる経路が存在しないため、検証を素通りされる余地がない。

### 7.3 ノウハウ集は対象外

ノウハウ集は台帳へ書き込まないため、バージョン検証の対象としない。
頻繁な更新を妨げないため。

## 8. 期限管理

### 8.1 管理する期限

1. 部材の納期（届く日）
2. 依頼への回答・承認期限
3. **現地で使う日（逆算の基準）**
4. 発注手続きの締切

**注**: 「納期」と「現地で使う日」は**別の期限**である。列を分けて持つこと。

### 8.2 逆算

**現地使用日を起点に、手配方法マスタのリードタイムで各段階の「必要な作業日」を算出する。**

```
現地使用日 → 納期 → 発注締切 → 承認期限
```

この「必要な作業日」が、遅延通知の判定基準となる。

## 9. 通知

### 9.1 基本原則

**順調なら黙る、遅れたら鳴る。**
担当者の能動的な作業が終わった時点（納品待ち）で、その担当者への通知は止める。

### 9.2 通知一覧

| # | 発火条件 | 宛先 | 回数 |
|---|---|---|---|
| 1 | 担当者に割り当てられた | 新担当者 | 1回 |
| 2 | 担当者が変更された | 新担当者 | 1回 |
| 3 | 納品待ちに到達した | 担当者 | 1回（担当者への最後の通知） |
| 4 | 各作業締め日までに未着手 | 担当者 | **締め日ごとに複数回** |
| 5 | 納品確認 | **起票者** | 1回 |

### 9.3 融合時の通知

融合により担当を失った旧担当者へ、**1回だけ**通知する。

### 9.4 メンション実装

- 本文に `@氏名` と文字列で書いても平文表示になり、通知は飛ばない
- **`ユーザーの @mention トークンを取得する` アクションが標準で利用可能**
- 台帳の担当者列は SharePointの Person型 で保持する

### 9.5 投稿者

**通知は「フロー ボット」名義で投稿する。**
ユーザー名義だと、全員への自動通知が特定個人の手動送信のように見えるため。

### 9.6 カードによる操作

通知にはステータス更新の操作を付ける（§5.5）。

### 9.7 投稿先

**通知はチャネルへ投稿する。**

他人宛ての通知も全員に見えるが、以下の理由から許容する。

- **チャネルの通知は既定でオフに設定する運用とする**（§4.8.1）
  個人宛てのメンションは、その設定に関わらず必ず通知される
- 経緯が全員に見えるため、後から状況を把握しやすい

**留意点**: カードによる操作（§5.5）をチャネルに出すと、
**担当者以外も送信できる**。応答者の検証を行う（§5.6）。

チャネル投稿では、以下のメンションが使える（`環境台帳.md` §C-2）。

| 種類 | アクション |
|---|---|
| 個人 | ユーザーの @mention トークンを取得する |
| **役割（タグ）** | チーム タグの @メンション トークンを取得する |

**タグを使えば、個人名をマスタに持たずに役割宛てへ通知できる。**
承認者への通知など、担当者が固定されない宛先で活用の余地がある。

## 10. 融合・分割

### 10.1 融合の条件

- **手配方法が同じもの同士のみ**
- **両方が発注前の段階にあること**
- 起票をまたぐことは**許可する**

**注**: このガードは自作UI側で効かせるものであり、台帳を直接編集された場合は素通りする。

### 10.2 項目の扱い

| 性質 | 例 | 扱い |
|---|---|---|
| **合算** | 数量、金額 | 足す |
| **選択** | 手配方法、担当者、備考 | どちらかを選ぶ |
| **推奨つき選択** | 期限 | **早いほうを推奨。変更は可能** |
| **連結** | 備考、参照リンク | 両方残す |

### 10.3 期限変更時の扱い

推奨から変更した場合、**画面に警告を表示し、変更した事実を台帳に記録する**。

### 10.4 選択UIの方針

**値が食い違う項目のみ提示し、一致する項目は自動確定する。**

### 10.5 消える側の扱い

物理削除せず、**「融合済み」ステータスで残し、統合先のIDを保持する**。

### 10.6 逆操作

**v1では「融合直後の取り消し」のみ実装する。**

## 11. 削除の扱い

### 11.1 方針

**物理削除は行わない。論理削除とする。**

- 「削除フラグ」列を持ち、既定ビューでは非表示にする
- フラグを立てられるのは**起票者のみ**（ツール側で制御）

### 11.2 理由

SharePointの標準機能では「起票者だけが削除できる」を実現できない。
アイテムレベル権限を使うと「自分の行しか編集できない」も同時にかかり、
担当者が他人の行を更新できなくなるため、業務フローと衝突する。

### 11.3 権限設定

**カスタム権限レベルの作成が可能であることを確認済み**（`環境台帳.md` §B-3）。

- Contribute（投稿）をコピーし、**Delete Items を外す**
- **リスト設定 →「このリストに対する権限」→ 継承を停止 → 対象リストのみに割り当てる**
- 権限レベル一覧へは `（サイトのURL）/_layouts/15/role.aspx` から直接アクセスする

## 12. メンテナンス機能

### 12.1 位置づけ

**管理者専用の単一HTML。全マスタを編集し、起票UIとノウハウ集を生成する。**

### 12.2 対象マスタ

| マスタ | 埋め込み先 |
|---|---|
| 部材マスタ / フォーマット定義 / 担当者マスタ / 文面マスタ | 起票UI |
| 手順ステップマスタ / メール定型マスタ | ノウハウ集 |
| 手配方法マスタ | 両方 |
| 許可バージョンマスタ | **SharePointリスト**（ここでは扱わない） |

### 12.3 設計方針

**すべて同じ形（一覧 → 編集 → 保存）に統一する。**
編集結果は、マスタを埋め込んだ**新しいHTMLファイルとして書き出す**。

### 12.4 フォーマット定義の半自動生成

- **Excelの「品名の並び」を貼り付けると、フォーマット定義の雛形が生成される**
- 各要素に部材マスタの内部コードを割り当てる（品名が一致すれば候補提示）
- フォーマット変更時も、貼り直すことで更新できる

**日常の起票では数量の並びだけを貼る。品名の並びを貼るのは登録・更新時のみ。**

### 12.5 手順ステップの編集

分岐構造を持つため、表形式での編集には限界がある。

- **本文・宛先・リンクはExcelから貼り付けて取り込める**ようにする
- **分岐の接続はメンテナンス画面上で組む**

### 12.6 スクリーンショットの点検

ノウハウ集の未挿入スクリーンショットを一覧表示する（§4.11）。
