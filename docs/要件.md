## 1. スコープ

### 1.1 本書で定義するもの

台帳のデータ構造 / 起票 / ノウハウ集 / マスタ群 / ステータスと業務フロー /
期限管理と逆算 / 通知 / 融合・分割 / 削除 / マスタ編集 / バージョン管理

### 1.2 未定義

- ノウハウ集の**中身**（手順そのもの）は、運用しながら整備していく
- 手配方法ごとの具体的なステップ、リードタイム、判定条件
- マスタの実データ（分類コード体系、部材、フォーマットの並び）

### 1.3 実現方式（環境調査で確定）

- **台帳は SharePointリスト**
- **ファイル置き場および各ツールの配布先はBox**（起票の受付口を除く）
- 通知・双方向連携は Power Automate の標準コネクタで実現可能
- 起票ツールからの直接書き込みは不可 → §3.10 のファイル方式で代替
- グリッドビューへの貼り付けは不採用（`環境台帳.md` §X）

### 1.4 成果物の構成

| ファイル | 役割 | 配布 |
|---|---|---|
| **起票ツール** (`kihyou.html`) | 起票、明細作成、分割、JSON出力 | 全員。バージョン管理下（§7） |
| **マスタ編集ツール** (`master_editor.html`) | マスタJSONの作成・編集 | 管理者のみ |
| **ノウハウ集** (HTML) | 手順の参照、メール生成、ノウハウ投稿 | 全員。気軽に更新 |

**起票ツールとノウハウ集を分離する理由**

- 更新頻度が違う。ノウハウ集は頻繁に更新するが、起票ツールはバージョン管理下にある
- 読む人が違う。ノウハウ集は起票しない担当者も参照する

## 2. データ構造

### 2.1 3層構造

```
起票（親）              … 部材群1つ分の依頼。1起票＝1部材群
 └ 明細                 … 部材1点＋数量。数量データの実体
     ↓ 手配方法でグルーピング
    手配タスク（子）     … 作業・ステータス・期限・通知の単位
```

**部材群は独立した層ではなく、起票の属性である。**

### 2.2 各層の役割

| 層 | 役割 |
|---|---|
| **起票（親）** | 部材群、納入先、納品日、起票者、手配主担当、手配副担当、確認記録 |
| **明細** | 部材1点＋数量。所属する手配タスクは常に1つ |
| **手配タスク（子）** | 作業の単位。ステータス・担当者・期限・通知はすべてここに付く |

### 2.3 明細と手配タスクの関係

- **1つの起票から複数の手配タスクが生まれる**（1対多）
- 明細層を挟むことで、手配タスクが複数の起票の明細を抱えても構造は壊れない
- **起票をまたぐ融合を禁止する制約は設けない**

### 2.4 起票者の保持（重要）

SharePointの `登録者` 列は、**フロー経由で作成された行では「接続作成者」になる**
（`環境台帳.md` §C-5）。**実際の起票者を保持する列を別途持つこと。**

### 2.5 起票ID

**各起票にUUIDを付与する。** 重複取り込みの防止に使う（§3.11）。
親リストの起票ID列には**一意制約を設定する**（`環境台帳.md` §B-2）。

### 2.6 担当者の列構成

| 列 | 型 | 内容 |
|---|---|---|
| 手配主担当 | Person型（単一） | **必須。1名** |
| 手配副担当 | Person型（複数） | 任意。0名以上 |

**Person型で複数値を許可できるかは未検証**（`環境台帳.md` の未確認事項）。
不可の場合は、副担当をメールアドレスの複数行テキストで持ち、
通知フロー側で分解する形に変更する。

## 3. 起票

### 3.1 起票の単位

**1起票 ＝ 部材群1つ。**

1つの手配は同一の納地へ納入されるという運用ルールがあるため、
納地が異なれば起票が分かれる。

### 3.2 セッション（複数起票）

1回の作業で複数の起票を作成できる。これは**UIの機能であり、データ構造ではない**。

- 起票を追加すると、**直前の起票から属性を転記できる**
  （納入先 / 納品日 / 起票者 / 手配主担当 / 手配副担当）
- 転記した内容は個別に手入力・修正できる

### 3.3 入力の流れ

```
1. 部材群を選ぶ
     └ 前提条件を表示し、確認チェックを取る（§3.9）
2. 数量を入力する
     ├ フォーマットを選ぶ（候補は提示するが確定は人）
     ├ Excelから貼り付け
     └ 手で足す
3. 起票の情報を入力する
4. 分割結果を確認する ← 明示的な確認が必要（§3.10）
```

**完了した段階は緑で表示し、次へ進むと自動で折りたたむ。**
見出しをクリックすれば何度でも開き直せる。

### 3.4 Excelフォーマットの構造

- **品目は一方向に並び、数量はそれと直交する方向に並ぶ**
  （行ベクトル形式 / 列ベクトル形式）
- **同一の部材群に、複数のバリアントが存在する**
  - 並び順が異なり、載っている部材にも差がある
  - 形状（縦横）が異なる場合がある
- 結合セル、セル内改行、数式エラー、セルコメントが混在する
- **貼り付けるのは数量の並びのみ**

### 3.5 貼り付けデータの解釈

**貼り付けたデータには、部材を示す情報が一切含まれない。** 位置だけが手がかりとなる。

```
貼り付けた値の位置（N番目）
  ↓ フォーマット定義（§6.3）
内部コード
  ↓ 部材マスタ（§6.2）
分類コード
  ↓ 手配方法マスタ（§6.4）
手配方法 → 通る段階 / リードタイム / ノウハウ集の該当手順
```

### 3.6 位置合わせのリスクと対策

**並びが1つずれると全明細が誤り、しかも静かに誤る。** 4段で防ぐ。

**① 選択は必ず人が行う**
形状と要素数から候補を提示するが、**確定は人が選ぶ**。

**② 並びのプレビュー**
フォーマットを選ぶと、**貼り付ける前に**その並びを一覧できる。
要素数が多くなるため、高さを固定したスクロール表示とし、
画面幅に応じて列を自動で増やす。

**③ 要素数の検証**
期待要素数と照合し、**一致しなければ取り込みを保留する**。

**④ 取り込み結果の目視確認**
「N番目 ＝ 品名 ＝ 数量」の形で一覧表示する。
**位置番号を画面上で最も強く表示する**（このツール最大の危険箇所であるため）。

### 3.7 貼り付けの再取り込み

**貼り付けた生テキストを起票ごとに保持する。**

フォーマットを後から選んだ場合、または選び直した場合、
**自動で取り込み直す**。貼り付けの順番を気にしなくてよい。

### 3.8 値の扱い

| 値 | 扱い |
|---|---|
| `0` / 空欄 | **不要とみなし、明細を作らない** |
| 数式エラー / 数値以外 | **スキップし、警告を表示**。取り込みは止めない |
| 桁区切りのカンマ | 除去して数値として読む |

### 3.9 手入力と貼り付けの共存

**貼り付けても、手入力した明細は消さない。** 貼り付け由来の明細だけを入れ替える。

**同じ部材が両方に現れた場合は、選ばせる。**

```
「品名C ケーブル」が手入力（5）と貼り付け（10）の両方にあります
  [ 合算する（15） ] [ 貼り付けの値を使う（10） ] [ 手入力の値を使う（5） ]
```

黙って合算すると、意図しない数量になったとき気づけないため。

手入力で既存の部材を再度足そうとした場合も、合算するか別行にするかを確認する。

### 3.10 起票の属性

| 項目 | 形式 | 必須 |
|---|---|---|
| **起票タイトル** | テキスト | **必須**（マスタで変更可） |
| **任意の補足** | テキスト | 任意（マスタで必須にできる） |
| 納入先情報 | **複数行の自由記述テキスト1つ** | 任意（未定可） |
| 納品日 | 日付 | 任意（未定可） |
| 起票者 | 担当者マスタから選択 | 任意（未定可） |
| **手配主担当** | 担当者マスタから選択（1名） | **必須** |
| **手配副担当** | 担当者マスタから複数選択 | 任意（不在可） |

**「未定」は明示的なチェックとして持つ。** 空欄（入れ忘れ）と区別するため。

**手配主担当のみ必須とする。** 未定のまま台帳に流れると、誰も動かないタスクが生まれるため。
ただし**管理者モードでは主担当も未定にできる**（試験や例外運用のため）。

#### 3.10.1 起票タイトル

**台帳に載る名前を、起票ごとに人が付ける。** 親リストの識別子となる。

```
{起票タイトル}_{部材群}_{任意の補足}
  例: 9月分手配_部材群A_追加分
```

- **組み立てのパターンはマスタで変更できる**（区切り文字・順序・要素の増減）
- **値が空の項目は、隣接する区切り文字ごと取り除かれる。** 区切りが余ることはない
- 組み上がった名前は、入力しながら画面に表示する
- **続けて起票する場合、起票タイトルだけを引き継ぐ**（任意の補足は空欄に戻す）

出力JSONには、組み上がった `title` と、分解した `titleBase` `titleSuffix` の両方を含める。

#### 3.10.2 納入先を構造化しない理由

各種のフォーマットが既にテキスト形式で存在しており、**貼り付けるだけで済む形が最も速い**。
項目ごとに分割させると、貼ったテキストを手で切り分ける作業が発生する。

代わりに、以下で「何を書くべきか」を伝える。

- **入力欄の上に、書くべき項目を常時表示する**（薄字の記入例だけでは、入力後に消えてしまうため）
- 見出しと項目はマスタで管理し、**部材群ごとに切り替えられる**

### 3.11 前提条件の確認

手配方法や部材群によっては、**本ツールのスコープ外の作業の完了を契機として着手する**ものがある。
システムは完了を判定できないため、**確認を促し、確認した事実を記録する**。

- 部材群を選んだ時点で表示する
- **その部材群のフォーマットに含まれる部材から、実際に使われる手配方法だけを拾う**
  （関係のない手配方法の注意を出さない）
- フォーマットを持たない部材群は、手入力で任意の部材を選べるため全件を対象とする
- **メッセージごとにチェックボックスを置き、すべて確認しないと次へ進めない**
- 前提条件は配列で持ち、件数は可変とする

### 3.12 分割ロジック

#### 3.12.1 基本規則

**同じ手配方法の明細を1つの手配タスクにまとめる。**

```
手配タスク ＝ 起票 × 手配方法
```

**手配方法だけで束ねれば、手配先と納地も結果的に揃う。**
手配先が違えば手配方法も違い、納地は起票単位で一致するため（§3.1）。

#### 3.12.2 担当者の継承

```
起票時      … 手配主担当（必須）と手配副担当（任意）を指定
分割後      … 全タスクに継承
ステータス2 … タスクごとに変更
```

#### 3.12.3 分割の実行場所

**起票ツールの中で分割まで完了させる。** 親・明細・タスクを含むJSONを生成する。
そのため**起票ツールは部材マスタと手配方法マスタを保持する**（§3.14）。

#### 3.12.4 例外の吸収

同じ手配方法でも分けたい場合は、ステータス2の確認画面で**手動分割**する。

### 3.13 分割結果の確認

**確認を明示的な操作とする。** 素通りできてはならない。

- タスクは**期限が早い順**に並べる
- **タスクごとにチェックボックス**を置く（10〜20件になりうるため、どれを見たか分かる形にする）
- **「すべて確認した」「すべてクリア」**の一括操作を用意する
- 確認済みのタスクは緑で表示する
- **すべて確認するまで、この段階は完了しない**
- **明細または納品日が変わったら、確認を自動でクリアする**
  （確認済みの状態が信用できなくなるため）

#### 3.13.1 表示

```
手配タスク 3 件   最も早い締切 09-16   確認 1/3   [すべて確認した][すべてクリア][すべて折りたたむ]

☐ T1  手配方法A   3品目 / 計57  最短 09-16
☑ T2  手配方法B   1品目 / 計10  最短 08-31
☐ T3  手配方法C   1品目 / 計3   最短 09-09
```

- 番号は `T1` 形式とし、工程の番号と見分けがつくようにする
- 各タスクは個別に開閉でき、一括の開閉もできる
- **期限が7日以内のタスクは強調する**
- 見出しの直下に説明文を表示する（マスタで変更可能）

### 3.14 完了後の選択

分割結果の確認まで済んだら、**次の行動を2択で提示する**。

```
[ このまま台帳へ送る ] [ 続けて別の起票を行う ]
```

未確認の段階では、この2択を出さず、残り件数を表示する。

### 3.15 台帳への送信

#### 3.15.1 方式

**ファイル方式に一本化する。**

```
起票ツール → JSONファイル
   ↓ 人がドラッグ＆ドロップで配置
［起票受付ライブラリ］（SharePointドキュメントライブラリ）
   ↓ トリガー発火（標準）
Power Automate
   ↓ SharePoint に HTTP 要求を送信します（標準）
［親リスト］［明細リスト］［タスクリスト］
```

- **ファイル名は起票ツール側で一意に生成する**（日時＋短縮ID）
- 明細には **`initialQuantity`（初期数量）** を含める。取り込み時に数量と同じ値を書き、
  以後 **数量 ≠ 初期数量 であれば台帳上で変更されたと判定できる**（§11.4）
- 拡張子は `.json` とし、**フローは他の拡張子を弾く**
- ファイル名を人が変更しても取り込みは正常に動作する（起票IDは中身にあるため）
- 取り込み後、状態別フォルダへ移動する（`取込済` / `重複スキップ` / `エラー`）

#### 3.15.2 即時反映

自動トリガーはポーリングのため数分のラグがある。急ぐ場合は、
**「手動でフローをトリガーします」型のフローを1本用意し、そのURLへのリンクを案内に載せる。**

- 中身は「受付フォルダの未処理ファイルをすべて取り込む」
- **単独・複数のいずれのファイルも取り込めるようにする**
- 利用者はリンクを開いて [実行] を押すだけでよい
- ファイルを選択する操作が不要で、**リンクで直接飛べる**

予備として、ライブラリでファイルを選び `[統合] → [フロー]` から実行する経路も残す。

**フローのURLを開いて実行できるかは未検証**（`環境台帳.md` の未確認事項）。

#### 3.15.3 案内文

```
台帳へ送る手順

1. 下の「JSONファイルを保存」を押します
2. 保存したファイルを ▶起票受付ライブラリ にドラッグして入れます
3. 台帳への取り込みは自動で行われます（反映まで数分かかることがあります）

急ぐときは ▶取り込みを今すぐ実行 を開き、[実行] を押してください
```

- **手順は番号付きにする**
- リンクの表示名とURLは**すべてマスタで管理する**
- 即時反映は独立させる（通常は読まなくてよい情報のため）

#### 3.15.4 送信後の動線

送信画面から**「別の起票を追加する」で入力画面へ戻れる**。
戻った時点で、確定済みの起票はセッションに保持されている。

### 3.16 重複取り込みの防止

**フローによる判定** — 起票IDが既に台帳にあれば取り込まない。
ファイルは `重複スキップ` フォルダへ移動する。

**一意制約** — 親リストの起票ID列に「固有の値を適用する」を設定する。
設定時に「インデックスを付けますか？」というダイアログが出るが、OKで進む。

| リスト | 起票ID | 一意制約 |
|---|---|---|
| 親 | 1行に1つ | **あり**（門番） |
| 明細 / タスク | 同じIDが複数行 | なし |

### 3.17 起票ツールの実装方針

#### 3.17.1 形態

- **自作の単一HTML**。標準フォームでは実現できない
- 外部ライブラリを使わず、ブラウザ内で完結
- 行ベクトル／列ベクトルは転置処理で両対応

#### 3.17.2 マスタの保持

**マスタはHTMLに埋め込む。外部JSONファイルの読み込み方式は採用しない。**

**理由**: 外部ファイルが必要なことを理解していない利用者がいるため、
**ファイル単体で動作しない仕組みは採用できない**。

#### 3.17.3 管理者モードによる自己再生成

**起票ツール自身が、新しいマスタを埋め込んだ新版を書き出せる。**

```
kihyou.html?admin=1
  1. マスタのJSONを貼り付ける
  2. 版数と更新日を入れる（版数は自動で+1される）
  3. [検証する] → エラーが1件でもあれば保存できない
  4. [新しい起票ツールを保存] → kihyou_vX.Y.Z.html
```

- 起動直後に自分自身のソースを保持し、**マスタのブロックだけを差し替える**
- 通常の利用者には管理者パネルは一切表示されない
- パネルは何度でも開閉できる
- **マスタの一時編集機能は設けない**（各利用者のマスタが分岐するため）

**これにより、部材数・部材群数・フォーマットの要素数が変わっても、
HTMLを改修する必要がない。** 改修が必要になるのは、
マスタに新しい種類の項目を追加する場合のみ。

#### 3.17.4 版数の表示

画面上部に**版数・更新日・マスタのハッシュ**を小さく表示する。

```
部材手配 起票ツール    v0.2.0  2026-08-12  e3024b23
```

ハッシュは同じ版数でも中身が違えば変わるため、配布物の同一性を確認できる。
出力JSONにも同じものを含める。

## 4. ノウハウ集

### 4.1 位置づけ

**作業のすべての入口。「困ったらここを開く」を1箇所に定める。**

### 4.2 形態と制約

**別の単一HTML。** 台帳とは連携できないため、**利用者が手配方法を自分で選ぶ**。

**HTMLから外へ出ていく操作は問題なく動作する**（検証済み）。
リンク、`mailto:`、Formsの起動、同一フォルダの別HTMLへのパラメータ付き遷移。

### 4.3 手順ステップの構造

**手順を部品化し、手配方法はその並びを指す。**
共通ステップを1つ書いて複数から参照する。

```
手順ステップマスタ
├ ステップID / タイトル / 説明
├ リンク（ツール／フォルダ）＋そこでの作業内容
├ メール定型ID
├ 所属ステータス
└ 次のステップ（条件つきで複数可）
```

### 4.4 分岐ナビゲーション

**現在のステップと、そこから進める選択肢だけを表示する。**
全体を俯瞰する表示も併せて用意する。

### 4.5 メール定型（Outlook連携）

**`mailto:` リンクで実現する。動作を確認済み**（`環境台帳.md` §F）。
件名の日本語、本文の改行、記号、差し込み値のいずれも正常。

**制約**: 本文長の上限、書式なしテキストのみ、添付不可。

**既定のメールアプリ**が2種類存在する環境のため、
§4.8 の「環境の準備」に設定手順を記載する。

### 4.6 前提条件の表示

手順の冒頭に、その手配方法の前提条件をチェックリストとして表示する。

### 4.7 起票ツールからの導線

送信完了画面から、生成された手配タスクごとに該当手順を開く。
同一フォルダに配置し、相対リンク＋URLパラメータで手配方法を渡す。

Teams通知からのリンクは行わない（ローカルファイルは開けないため）。

### 4.8 §0「はじめに」

```
0. はじめに
   ├ 0-1. 環境の準備
   │   ├ 既定のメールアプリの設定（初回のみ）
   │   └ Teamsのチャネル通知設定（§4.8.1）
   ├ 0-2. 起票のしかた
   └ 0-3. 台帳への送り方
```

**0-1 は初回のみ必要なため、既定で折りたたむ。**

#### 4.8.1 Teamsのチャネル通知設定

通知はチャネルへ投稿するため（§9.7）、
**チャネルの通知を絞り、自分がメンションされたときだけ気づく**設定を案内する。

**個人宛てのメンションは、設定に関わらず必ず通知される。**

メニュー名は環境によって異なる可能性があるため、
スクリーンショットは §4.11 のプレースホルダ規約で用意する。

### 4.9 ノウハウ投稿

Microsoft Forms の**事前入力パラメータ**を使う。

- 手配方法とステップは**自動で埋まる**。書くのは1項目だけ
- **投稿は即座には反映されない**。管理者が採否を判断して次版へ反映する
- **事前入力済みURLは、Formsの専用機能で取得**し、マスタに登録する
- **必ず正式形のURLを使う**（短縮形では転送時にパラメータが消える）

### 4.10 注意点の集積は行わない

必要な注意事項は該当する手順ステップの説明に直接書き込む。

### 4.11 スクリーンショットの扱い

環境の画面はリポジトリに含められない。
**HTMLにはプレースホルダのみを置き、画像は別途挿入する。**

```html
<!-- SCREENSHOT: 何を撮るべきかをここに書く -->
<figure class="shot" data-shot="識別子">
  <img src="img/識別子.png" alt="説明">
  <figcaption>キャプション</figcaption>
</figure>
```

- 画像が無くても**表示は崩れない**
- `data-shot` により、**未挿入の一覧を機械的に取得できる**
- **`img/` は `.gitignore` に含める**

## 5. ステータスと業務フロー

### 5.1 標準の流れ

**親レベル**: 1. 起票者記票 / 2. 行自動振り分け確認・手動修正

**子（手配タスク）レベル**: 3. 発注ノウハウ確認 / 4. 見積取得 / 5. 発注 /
6. システム処理・上司承認 / 7. 発注完了確認 / 8. 納品確認 / 9. 検収確認

### 5.2 段階の可変性

段階は**ほぼ共通**だが、手配方法によって**スキップまたは大幅に変わる**。
ステータスの流れを実装に埋め込まず、**手配方法マスタに持たせる**。

### 5.3 ステータス3「発注ノウハウ確認」

**ノウハウ集の該当手順を開いて確認する。記録は残さない。**
完了操作は Teams通知のカードから行う（§5.5）。

### 5.4 検収の自動クローズ

**未完了でも2か月経過したらタスク終了とする。**
日次のスケジュール処理で実現し、**自動クローズのフラグを残す**。

### 5.5 Teamsからのステータス更新

**動作を確認済み**（`環境台帳.md` §H）。

- 「アダプティブ カードを投稿して応答を待機する」は標準
- **選択肢・日付・自由記述の3種類とも表示され、値が正しく返る**（日本語を含む）
- 応答には `messageLink` が含まれるため、**台帳の行から該当の通知へリンクを張れる**

### 5.6 応答者の検証

通知はチャネルへ投稿するため、**手配担当者以外もカードを操作できる**。

```
応答者 ＝ 手配主担当 または 手配副担当のいずれかか？
  ├ 一致   → 通常どおり更新
  └ 不一致 → 別処理（§5.6.2）
```

#### 5.6.1 前提の確認（未検証）

**カードの応答に、応答者を識別できる情報が含まれるか**は未確認。

**確認手順**: まず実行履歴の出力を全項目確認する。
応答者らしき項目が無ければ、その時点で「不可」と確定する。
項目があった場合は、**担当者以外の人に1度押してもらい、値が変わるかを確認する**
（自分だけで押しても、宛先と応答者を区別できないため）。

#### 5.6.2 不一致だった場合の処理（未定）

| 案 | 内容 |
|---|---|
| 拒否 | 台帳を更新せず、応答者へ返す |
| 警告つき更新 | 更新はするが、双方へ通知する |
| **代理操作として記録** | 更新し、誰が代理で操作したかを残して担当者へ通知する |

**3案目が実務に合う可能性がある。** 運用を見てから決める。

### 5.7 テキスト返信によるステータス更新（v2以降の候補）

スレッドへの返信で更新できると、携帯端末からの操作で利便性が上がる。

**未検証**: トリガーがスレッド返信で発火するか、`messageLink` から特定できるか。

**本文の解釈は厳密な合図に限定する**（`!done` `!hold` `!date 9/23` など）。
自然文の解釈は行わない。表記の揺れが無限にあり、誤判定の温床になるため。

**カード操作を主、テキスト返信を補助とする。**

## 9. 通知

### 9.2 通知一覧

| # | 発火条件 | 宛先 | 回数 |

## 11. 削除の扱い

**物理削除は行わない。論理削除とする。**

- 「削除フラグ」列を持ち、既定ビューでは非表示にする
- フラグを立てられるのは起票者のみ（ツール側で制御）

**理由**: SharePointの標準機能では「起票者だけが削除できる」を実現できない。
アイテムレベル権限を使うと「自分の行しか編集できない」も同時にかかり、
担当者が他人の行を更新できなくなる。

**権限設定**: Contribute をコピーし **Delete Items を外す**。
**対象リストのみに割り当てる**（サイト全体に適用すると副作用が出る）。
権限レベル一覧へは `/_layouts/15/role.aspx` から直接アクセスする。

### 11.4 明細の数量変更の可視化

台帳上で明細の数量を直接変更する運用がある（既存の手配へ追加する場合など）。
**変更された明細を、一覧で見分けられるようにする。**

```
明細リスト
├ 数量        … 現在の値。人が変更できる
└ 初期数量    … 起票時の値。以後変えない
```

- 取り込み時に、フローが両方へ同じ値を書く
- **数量 ≠ 初期数量 の行を、列の書式設定で強調する**
- 通知は行わない。表示で目立たせるだけとする

バージョン履歴との比較よりも単純で、かつ画面上で常時見えるため、この方式を採る。

## 12. マスタ編集ツール

### 12.1 位置づけ

**管理者専用の単一HTML。マスタのJSONを作る道具に徹する。**

**このツール自身はマスタを保持しない。** 読み込み → 編集 → 書き出し。

```
マスタ編集ツール → JSON
      ↓ コピー
起票ツール?admin=1 → 新しい起票ツール
```

### 12.2 タブ構成

読み込み・書き出し / 分類 / 部材 / 手配方法 / 部材群 / フォーマット / 担当者 / 文面・URL

### 12.3 工数を減らす仕掛け

**手でJSONを書くのは現実的ではない。** 特にフォーマットの並びは、
要素数が多い場合に1つずれても気づけない。**このツールで最も事故が起きやすい場所を、
最も手作業に頼る形にしてはならない。**

#### 12.3.1 Excelからの一括登録

| マスタ | 貼り付ける列 |
|---|---|
| 分類 | コード / 名称 / 説明 |
| 部材 | 品番 / 品名 / 分類コード |
| 担当者 | 氏名 / メールアドレス |

- **部材の内部コードは自動採番する**
- 品番または品名が一致する既存行は更新し、なければ追加する
- 既存を全置換するかどうかを選べる

#### 12.3.2 分類の一括割り当て

**分類コードの割り当ては業務判断であり、自動化できない。**
最も時間がかかる作業のため、以下で短縮する。

- 行を複数選択して**まとめて分類を変更**
- **「分類なしを選択」** で未設定の行だけを選べる

#### 12.3.3 フォーマットの並びの半自動生成

**Excelの品名の並びをそのまま貼り付ける。**

```
1  品名A 12インチ  → P-000001  自動
2  品名Ａ　8インチ → P-000002  自動（全角・空白を吸収）
3  AAA-001        → P-000001  自動（品番でも照合）
4  品名X 未登録    → 一致なし。選択リストから選ぶ
```

- **全角・半角・空白の有無を吸収して照合する**
- **品名だけでなく品番でも照合する**
- 向きは貼り付けた形から自動で判定する
- **一致しなかった行は赤く表示し、貼り付けた元の文字列を横に残す**
  （何を選べばよいか分かるようにするため）
- 一致件数と未一致の一覧を表示する

### 12.4 検証

**起票ツールと同じ規則で検証する。** ここで通れば向こうでも通る。

| 検出する誤り | 種別 |
|---|---|
| 内部コードの重複 | エラー |
| フォーマットに存在しない部材 | エラー |
| 分類マスタにない分類コード | エラー |
| 手配方法のない分類コード | エラー |
| 存在しない部材群を指すフォーマット | エラー |
| 向きの未設定 | エラー |
| メールアドレスのない担当者 | エラー |
| メールアドレスの形式 | 注意 |
| フォーマットのない部材群 | 注意 |
| 受付ライブラリ・即時取り込みのURL未設定 | 注意 |

**エラーが1件でもあれば、起票ツール側で取り込めない。**

### 12.5 安全策

- **部材を消すとき、フォーマットで使われていれば警告する**
- **部材群を消すとき、フォーマットがあれば警告する**
- 部材の全置換を行うときは確認する
- 閉じようとしたときに確認する（保存していない編集を守るため）
