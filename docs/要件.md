## 1. スコープ

### 1.1 本書で定義するもの

台帳のデータ構造 / 起票 / マスタ群 / ステータスと業務フロー /
期限管理と逆算 / 通知 / 融合・分割 / 削除 / メンテナンス機能 / バージョン管理

### 1.2 未定義（次フェーズ）

- ノウハウ集の構造と台帳との接続
- Outlookメール自動出力
- フォームによる情報入力
- 「発注ノウハウ確認」ステータスで具体的に何が起きるか

### 1.3 実現方式（第1サイクルで確定）

- **台帳は SharePointリスト**
- **Boxは成果物ファイルの格納先、および起票UIの配布先**
- 通知・双方向連携は Power Automate の標準コネクタで実現可能
- **起票UIからの直接書き込みは不可**（プレミアム必須）→ §3.10 の方式で代替

## 2. データ構造

### 2.1 3層構造

```
起票（親）              … 部材群1つ分の依頼。1起票＝1部材群
 └ 明細                 … 部材1点＋数量。数量データの実体
     ↓ 手配方法でグルーピング
    手配タスク（子）     … 作業・ステータス・期限・通知の単位
```

**部材群は独立した層ではなく、起票の属性である。**
1回の起票では部材群を1つだけ選ぶ。複数の部材群を扱う場合は、起票を複数件作る（§3.2）。

### 2.2 各層の役割

| 層 | 役割 |
|---|---|
| **起票（親）** | 部材群、納入先、納品日、起票者、既定担当者を持つ |
| **明細** | 部材1点＋数量。所属する手配タスクは常に1つ |
| **手配タスク（子）** | 作業の単位。ステータス・担当者・期限・通知はすべてここに付く |

### 2.3 明細と手配タスクの関係

- **1つの起票から複数の手配タスクが生まれる**（1対多）
- 明細層を挟むことで、手配タスクが複数の起票の明細を抱えても構造は壊れない
- **起票をまたぐ融合を禁止する制約は設けない**（制約のほうが実装が増え、将来の正当なケースを塞ぐため）

### 2.4 起票者の保持（重要）

SharePointの `登録者` 列は、**フロー経由で作成された行では「接続作成者」になる**
（`環境台帳.md` の「コネクタの認証方式」参照）。

したがって、**実際の起票者を保持する列を別途持つこと。**
`登録者` を起票者として扱ってはならない。

### 2.5 起票ID

**各起票にUUIDを付与する。** 重複取り込みの防止に使う（§3.11）。
親リストの起票ID列には**一意制約を設定する**（設定可否は次サイクルで確認）。

## 3. 起票

### 3.1 起票の単位

**1起票 ＝ 部材群1つ。**

### 3.2 セッション（複数起票）

1回の作業で複数の起票を作成できる。これは**UIの機能であり、データ構造ではない**。
送信されたものは独立した起票がN件並ぶ。

- 起票を追加すると、**直前の起票から属性を転記できる**
  （納入先 / 納品日 / 起票者 / 既定担当者）
- 転記した内容は個別に手入力・修正できる

### 3.3 入力の流れ

```
1. 部材群を選択          ← 必ずユーザーが選ぶ
2. フォーマットを選択      ← 候補提示はするが、確定はユーザー
3. 数量を入力
     ├ Excelから貼り付け（フォーマットがある場合）
     └ UI上で選択・修正（フォーマットが無い／貼付後の修正）
4. 起票の属性を入力（§3.8）
5. 確認 → 次の起票へ、または送信
```

**貼り付けとUI編集は排他ではない。**
貼り付けた結果がそのまま編集可能な明細一覧となり、追加・削除・数量修正ができる。
フォーマットが無い部材群は、空の一覧から手で追加していく。**同じ画面の同じ操作**とする。

### 3.4 Excelフォーマットの構造（実物の観察結果）

- **品目は一方向に並び、数量はそれと直交する方向に並ぶ**
  - 行ベクトル形式: 品目が横に並び、数量を横一列に書く
  - 列ベクトル形式: 品目が縦に並び、数量を縦一列に書く
- **同一の部材群に、複数のバリアントが存在する**
  - 例: 社内用と社外用。**並び順が異なり、載っている部材にも差がある**（非公表部材など）
  - **形状（行ベクトル／列ベクトル）が異なる場合がある**
- 品目名の並びとは別に、品番の並びが存在する場合がある
- 結合セル、セル内改行、数式エラー、セルコメントが混在する
- **貼り付けるのは数量の並びのみ**。品目名や周辺の属性列は貼り付けない

### 3.5 貼り付けデータの解釈

**貼り付けたデータには、部材を示す情報が一切含まれない。** 位置（何番目か）だけが手がかりとなる。

```
貼り付けた値の位置（N番目）
  ↓ フォーマット定義（§6.2）
内部コード
  ↓ 部材マスタ（§6.1）
分類コード
  ↓ 手配方法マスタ（§6.3）
手配方法 → 通る段階 / リードタイム / ノウハウ集へのリンク
```

### 3.6 位置合わせのリスクと対策

**位置で判定する以上、並びが1つずれると全明細が誤り、しかも静かに誤る。**

**① 選択は必ずユーザーが行う**
- 貼り付けた形状（行／列ベクトル）と要素数から**候補を提示する**
- ただし**自動判定は参考情報にとどめ、確定は必ずユーザーが選択する**
- ユーザーが選ぶのは「部材群」と「どのフォーマットか」の2つ

**② 要素数の検証**
- フォーマット定義が持つ期待要素数と、貼り付けた要素数を照合する
- 一致しない場合は警告を出し、取り込みを保留する

**③ 取り込み結果の目視確認**
- 「N番目 ＝ 品名 ＝ 数量」の形で一覧表示し、確認後に確定する
- ステータス2「行自動振り分け確認・手動修正」がこの受け皿となる

### 3.7 値の扱い

| 値 | 扱い |
|---|---|
| `0` | **不要とみなし、明細を作らない** |
| 空欄 | 同上 |
| 数式エラー（`#VALUE!` 等） | **スキップし、警告を表示する**。取り込み自体は止めない |
| 数値以外の文字列 | 同上 |

要素数が多くても、実際に手配するのは数点であるため、明細は現実的な件数に収まる。

### 3.8 起票の属性

| 項目 | 形式 | 備考 |
|---|---|---|
| 納入先情報 | **複数行の自由記述テキスト1つ** | §3.8.1 |
| 納品日 | 日付 | 「未定」可 |
| 起票者 | 担当者マスタから選択 | 「未定」可 |
| 既定担当者 | 担当者マスタから選択 | 「未定」可。§3.9.2 |

**すべて「未定」を明示的に選択できる。**
空欄（入れ忘れ）と未定（意図的）を区別するため。
未定・空欄を含む起票は、台帳の一覧で識別できるようにする（後から埋めるべきものが分かる）。

**必須チェックは行わない。** 未入力のまま送信できる。

#### 3.8.1 納入先情報を構造化しない理由

各種のフォーマットが既にテキスト形式で存在しており、**貼り付けるだけで済む形が最も速い**。
項目ごとに分割させると、貼ったテキストを手で切り分ける作業が発生し、本末転倒となる。

代わりに、以下で「何を書くべきか」を伝える。

- **薄字のプレースホルダ**で記入例を示す
- 入力欄の近くに**ガイドラインを表示**する
- **ガイドラインの文面はマスタで管理し、部材群ごとに切り替える**（§6.5）

### 3.9 分割ロジック

#### 3.9.1 基本規則

**同じ手配方法の明細を1つの手配タスクにまとめる。**

```
手配タスク ＝ 起票 × 手配方法
```

明細が何件あっても、手配方法の種類数だけタスクが生成される。

**理由**: §9.1 で融合の条件を「手配方法が同じもの同士のみ」と定めた。
この分割は**最初から融合済みの状態で作る**ことと等価であり、分割と融合の粒度が一致する。
明細1件＝1タスクとすると、要素数の多いフォーマットで数十タスクが生まれ、
通知も数十回発生するため実務が回らない。

#### 3.9.2 担当者の決まり方

```
起票時      … 起票全体の既定担当者を1人指定（未定も可）
分割後      … 全タスクにその担当者を継承
ステータス2 … タスクごとに担当者を修正
```

§4.1 の「起票者記票（担当者割り当てを含む）」は、**既定担当者の指定**を意味する。

#### 3.9.3 分割の実行場所

**起票UI（ローカルHTML）の中で分割まで完了させる。**

v1ではPower Automateを経由しないため、UIが親・明細・タスクの3種類を生成する必要がある。
そのため**起票UIは部材マスタと手配方法マスタを保持する**（§3.13）。

#### 3.9.4 例外の吸収

同じ手配方法でも分けたい場合（発注先が違う等）は、
ステータス2の確認画面で**手動分割**する。

### 3.10 台帳への送信方式

起票UIから SharePoint へ直接書き込むことはできない
（「HTTP要求の受信時」トリガーがプレミアムのため）。以下の2方式を併用する。

#### 3.10.1 ファイル保存（常に実行）

**起票完了時、常にJSONファイルを生成し、指定のSharePointライブラリへ保存する。**

```
起票UI → JSONファイル
   ↓ 保存
［起票受付ライブラリ］（SharePointドキュメントライブラリ）
   ↓ トリガー発火（標準）
Power Automate
   ↓ SharePoint に HTTP 要求を送信します（標準）
［親リスト］［明細リスト］［タスクリスト］
```

- **ファイル名は起票UI側で一意に生成する**（例: `kihyou_YYYYMMDD_HHMMSS_<短縮ID>.json`）
- 取り込み後、ファイルは状態別のフォルダへ移動する
  - `取込済` / `重複スキップ` / `エラー`
  - **取り込まなかった場合も必ず移動させる**（受付フォルダに残るものが未処理、と分かるようにする）
- 反映まで**数分のラグがある**（トリガーのポーリング間隔による）
- **即時反映が必要な場合**は、ライブラリ上でファイルを選択し、
  メニューから手動でフローを実行する（手順の可否は次サイクルで確認）

**投入口をSharePointライブラリとする理由**: Box Driveの同期遅延を避けるため。
起票UI本体の配布先はBoxとする（§3.13.3）。

#### 3.10.2 テキスト貼り付け（急ぐとき用）

**3つのリストへ直接貼り付ける。反映は即座。**

貼り付けの順序は **親 → 明細 → タスク** とする。
順序を守らないと、親が存在しないのに明細だけが登録される破損状態が生じる。
親で重複を弾かれた場合は、そこで中止する。

**UIは、どのテキストをどのリストへ貼るかを明確に案内すること**（§3.12）。

#### 3.10.3 両方式の関係

**ファイル保存は常に行われる。テキスト貼り付けは追加の手段である。**

```
起票完了
  ↓
ファイルを指定フォルダへ保存（常に実行）
  ↓
急ぐ場合のみ、どちらか一方を実施
  ├ テキスト貼り付け（3リストへ）
  └ ライブラリで手動フロー実行
```

両方を実施しても二重登録は起きない（§3.11）。

### 3.11 重複取り込みの防止（双方向）

#### 3.11.1 ファイル → 台帳（既に貼り付け済みの場合）

フローが起票IDを確認し、**既に台帳に存在すれば取り込まない**。
ファイルは `重複スキップ` フォルダへ移動する。

#### 3.11.2 台帳 → 貼り付け（既に取り込み済みの場合）

**手段A: 列の一意性制約（本命）**
親リストの起票ID列に「一意の値を適用」を設定する。
重複した行は**物理的に登録できなくなる**。
（設定可否は次サイクルで確認）

**手段B: フローによる検知（併用）**
「項目が作成されたとき」トリガーで起票IDの重複を検知し、

- 該当行に警告フラグを立てる（書式設定で赤表示）
- 起票者へTeams通知「この起票は既に取り込み済みです」

手段Aが使えない場合の代替であり、使える場合も
標準エラーメッセージの分かりにくさを補う役割を果たす。

#### 3.11.3 起票IDの持たせ方

| リスト | 起票ID | 一意制約 |
|---|---|---|
| 親 | 1行に1つ | **あり**（これが門番） |
| 明細 | 同じIDが複数行 | なし |
| タスク | 同じIDが複数行 | なし |

親を守れば全体が守れる。

### 3.12 送信画面のUI要件

- **ファイル保存は常に実行される**旨を明示する
- 即時反映が必要な場合の選択肢を提示し、**どちらか一方のみ実施するよう案内する**
- テキスト貼り付けを選んだ場合、**どのテキストをどのリストに、どの順で貼るか**を
  段階的に明示する（3つのテキストを個別にコピーできること）
- ファイル方式には**取り込みまでラグがある**旨を表示する
- ファイル方式で急ぐ場合の**手動フロー実行の手順**を表示する
- 送信後、実施済みの方式が分かるようにする

**案内文の文面はマスタで管理する**（§6.5）。
実際のメニュー名やパスが想定と異なる場合、会社側で修正できるようにするため。

### 3.13 起票UIの実装方針

#### 3.13.1 形態

- **自作の単一HTML**。SharePointの標準フォームでは実現できない
- 会社環境に依存しないため、**自宅で完全に作り込める**
- **第1サイクルでローカルHTMLの動作とクリップボード解析の成立を確認済み**
  （`環境台帳.md` D-5）
- 外部ライブラリを使わず、ブラウザ内で完結させる
- 行ベクトル／列ベクトルは転置処理で両対応する

#### 3.13.2 マスタの保持方法

**マスタはHTMLに埋め込む。外部JSONファイルの読み込み方式は採用しない。**

**理由**: 起票UIは各利用者が手元に持つ。
外部ファイルが必要なことを理解していない利用者がいるため、
**ファイル単体で動作しない仕組みは採用できない**。

代償としてマスタ更新のたびにHTML全体を配り直すことになるが、
§3.13.3 の配布方法および §7 のバージョン管理と組み合わせることで許容できる。

**マスタのローカル編集機能は設けない。**
各利用者のマスタが分岐し、バージョン管理と衝突するため。

#### 3.13.3 配布

**Boxに配置する。** 差し替えれば、全員が次に開いたときに新版となる。

**注意**: Boxのウェブ画面から直接開いた場合、ブラウザで実行されない可能性がある。
Box Drive 経由でローカルファイルとして開く運用を想定する
（可否は次サイクルで確認）。

## 4. ステータスと業務フロー

### 4.1 標準の流れ

**親レベル**

1. 起票者記票（既定担当者の指定を含む）
2. 行自動振り分け確認・手動修正（起票者・担当者）

**子（手配タスク）レベル**

3. 発注ノウハウ確認
4. 見積取得
5. 発注
6. システム処理・上司承認
7. 発注完了確認
8. 納品確認
9. 検収確認

### 4.2 段階の可変性

- 段階は**ほぼ共通**だが、手配方法によって**スキップまたは大幅に変わる**場合がある
- **業務整理は未完了。整理が進むことを前提とした設計にする**
- ステータスの流れを実装に埋め込まず、**手配方法マスタに持たせる**
- 最初は数種類だけマスタに登録して運用を開始し、育てていく

### 4.3 検収の自動クローズ

- 検収確認は重要度が低い
- **未完了でも2か月経過したらタスク終了とする**
- 日次のスケジュール処理で実現する（スケジュールトリガーは標準で利用可）
- **自動クローズされた事実がわかるフラグを残す**

## 5. 自動振り分け

### 5.1 判定方法

- **部材の分類コードから機械的に決まる**（分類コードは部材マスタが保持する）
- **約9割は自動判定可能**
- 残り1割は特殊要素があり人が判断する → **v1では対象外**

### 5.2 人による確認

自動振り分けの結果は、**ステータス2で起票者・担当者が確認し、手動修正できる**。

## 6. マスタ群

**中身は業務固有情報のため、リポジトリには載せない。**
構造のみリポジトリで管理し、中身は会社側で登録する（`PROJECT.md` §4）。

### 6.1 部材マスタ

| 項目 | 内容 |
|---|---|
| **内部コード** | **システムが振る一意のキー。不変。意味を持たせない**（例: `P-000123`） |
| 品番 | 社内の品番。**空欄可**。表記ゆれ・重複はここで吸収する |
| 品名 | 表示名 |
| 分類コード | 手配方法の自動振り分けに使う（§5.1） |

**設計判断: 社内品番をキーにしない**
社内品番には表記ゆれと重複があるため、これをキーにすると明細の紐づけが破綻する。

**仮コードのフラグは持たない**
品番が空欄であれば未確定と分かるため、専用のフラグ列も、表示上の装飾も設けない。

### 6.2 フォーマット定義

**部材群 × バリアント**の単位で持つ。

| 項目 | 内容 |
|---|---|
| フォーマットID | 識別子 |
| 部材群 | どの部材群に属するか |
| バリアント名 | 例: 社内用 / 社外用 |
| 形状 | 行ベクトル / 列ベクトル |
| 期待要素数 | 検証に使う（§3.6②） |
| 並び | **N番目 → 内部コード** の対応表 |

同じ部材群でも、バリアントごとに独立した並びを持つ。
並び順が違っても、載っている部材が違っても、最終的に同じ内部コードへ解決される。

### 6.3 手配方法マスタ

| 項目 | 内容 |
|---|---|
| 手配方法コード | 識別子 |
| 判定条件 | この分類コードなら、この手配方法 |
| 使う段階 | 標準9段階のうちどれを通るか、スキップするか |
| 各段階のリードタイム | 逆算に使用（§8.2） |
| ノウハウ集へのリンク | 次フェーズで定義 |

### 6.4 担当者マスタ

**必須。** Person型列はディレクトリに実在するユーザーしか設定できず、
テキストでの自由入力ができないため（`環境台帳.md` B-3）。

| 項目 | 内容 |
|---|---|
| 氏名 | 表示名 |
| メールアドレス | Person型列への設定、およびTeamsメンションに使用 |

起票UIでは担当者を**選択式**とし、このマスタから選ばせる。

### 6.5 文面マスタ

UIに表示する案内文を保持する。実装に埋め込まない。

| 用途 | 内容 |
|---|---|
| 納入先ガイドライン | 部材群ごとに切り替え可能（§3.8.1） |
| 納入先プレースホルダ | 薄字で表示する記入例 |
| 送信手順の案内 | 貼り付け先、順序、手動フロー実行の手順（§3.12） |

**理由**: 実際のメニュー名・パス・記載ルールが想定と異なる場合、
会社側で修正できるようにするため。実装に埋め込むと修正のたびに往路が発生する。

### 6.6 許可バージョンマスタ（SharePoint側）

**このマスタのみ、起票UIではなくSharePointリストとして持つ。**

| 項目 | 内容 |
|---|---|
| バージョン | 例: `v1.3` |
| 状態 | 許可 / 非許可 |
| 備考 | |

検証フローがこれを参照する（§7.2）。
新版を配布したらこのリストに1行追加するだけでよく、ツール側の改修は不要。

## 7. バージョン管理

### 7.1 識別子

起票UIの出力（ファイル・貼り付けテキストの双方）に、識別子を埋め込む。

```
形式例: TLV|<バージョン>|<出力日時>|<マスタのハッシュ>
```

### 7.2 検証

**v1（貼り付け）**: 「項目が作成されたとき」トリガーで検証する。
不正なバージョンであれば、警告フラグを立て、起票者と管理者へ通知する。
**物理的に阻止はできないが、投入直後に検出できる。**

**v2（ファイル）**: フローが取り込み前に検証し、**不正なら取り込まない**。
ファイルは `エラー` フォルダへ移動する。

## 8. 期限管理

### 8.1 管理する期限

1. 部材の納期（届く日）
2. 依頼への回答・承認期限
3. **現地で使う日（逆算の基準）**
4. 発注手続きの締切

**注**: 「納期（届く日）」と「現地で使う日」は**別の期限**である。列を分けて持つこと。

### 8.2 逆算

**現地使用日を起点に、手配方法マスタのリードタイムで各段階の「必要な作業日」を算出する。**

```
現地使用日 → 納期 → 発注締切 → 承認期限
```

この「必要な作業日」が、遅延通知の判定基準となる。

## 9. 通知

### 9.1 基本原則

**順調なら黙る、遅れたら鳴る。**
担当者の能動的な作業が終わった時点（納品待ち）で、その担当者への通知は止める。

### 9.2 通知一覧

| # | 発火条件 | 宛先 | 回数 |
|---|---|---|---|
| 1 | 担当者に割り当てられた | 新担当者 | 1回 |
| 2 | 担当者が変更された | 新担当者 | 1回 |
| 3 | 納品待ちに到達した | 担当者 | 1回（担当者への最後の通知） |
| 4 | 各作業締め日までに未着手 | 担当者 | **締め日ごとに複数回** |
| 5 | 納品確認 | **起票者** | 1回 |

### 9.3 融合時の通知

融合により担当を失った旧担当者へ、**「担当分がタスクXに統合されました」を1回だけ通知する**。

### 9.4 メンション実装

- 本文に `@氏名` と文字列で書いても平文表示になり、通知は飛ばない
- **`ユーザーの @mention トークンを取得する` アクションが標準で利用可能**（`環境台帳.md` C-2）
- 台帳の担当者列は SharePointの Person型 で保持する

### 9.5 投稿者

**通知は「フロー ボット」名義で投稿する。**
ユーザー名義だと、全員への自動通知が特定個人の手動送信のように見えるため。

## 10. 融合・分割

### 10.1 融合の条件

- **手配方法が同じもの同士のみ**
- **両方が発注前の段階にあること**（発注済みとの融合は不可）
- 起票をまたぐことは**許可する**

**注**: このガードは自作UI側で効かせるものであり、台帳を直接編集された場合は素通りする。v1では割り切る。

### 10.2 項目の扱い

| 性質 | 例 | 扱い |
|---|---|---|
| **合算** | 数量、金額 | 足す |
| **選択** | 手配方法、担当者、備考 | どちらかを選ぶ |
| **推奨つき選択** | 期限 | **早いほうを推奨。ユーザーによる変更は可能** |
| **連結** | 備考、参照リンク | 両方残す |

### 10.3 期限変更時の扱い

- 推奨（早いほう）から変更した場合、**画面に警告を表示する**
- **推奨から変更した事実を台帳に記録する**

### 10.4 選択UIの方針

**値が食い違う項目のみ提示し、一致する項目は自動確定する。**

### 10.5 消える側の扱い

物理削除せず、**「融合済み」ステータスで残し、統合先のIDを保持する**。

### 10.6 逆操作

- **v1では「融合直後の取り消し」のみ実装する**
- 任意タイミングでの分割・再分割はv2以降

## 11. 削除の扱い

### 11.1 方針

**物理削除は行わない。論理削除とする。**

- 台帳に「削除フラグ」列を持ち、既定ビューでは非表示にする
- フラグを立てられるのは**起票者のみ**（ツール側で制御）

### 11.2 理由

- 台帳という性質上、行が消えるべきではない（誤操作、監査）
- SharePointの標準機能では「起票者だけが削除できる」を実現できない
  → アイテムレベル権限を使うと「自分の行しか編集できない」も同時にかかり、
    担当者が他人の行を更新できなくなるため、業務フローと衝突する

### 11.3 権限設定

**カスタム権限レベルの作成が可能であることを確認済み**（`環境台帳.md` B-4）。

- Contribute（投稿）をコピーしたカスタム権限レベルを作り、**Delete Items を外す**
- **リスト設定 →「このリストに対する権限」→ 継承を停止 → 対象リストのみに割り当てる**

## 12. メンテナンス機能

### 12.1 位置づけ

マスタ編集画面の**共通基盤**として設計する。今後増える前提。

### 12.2 対象マスタ

| マスタ | 保持場所 |
|---|---|
| 部材マスタ | 起票UIに埋め込み |
| フォーマット定義 | 同上 |
| 手配方法マスタ | 同上 |
| 担当者マスタ | 同上 |
| 文面マスタ | 同上 |
| 許可バージョンマスタ | **SharePointリスト** |

### 12.3 設計方針

**すべて同じ形（一覧 → 編集 → 保存）に統一する。**

編集結果は**起票UIへ埋め込む形で書き出す**（§3.13.2）。
メンテナンス機能と起票UIは別のHTMLとし、
メンテナンス側が新しいバージョンの起票UIを生成する形とする。

### 12.4 フォーマット定義の半自動生成

要素数が多いフォーマットを手で登録するのは現実的でない。

- **メンテナンス画面で、Excelの「品名の並び」を貼り付けると、フォーマット定義の雛形が生成される**
- 生成された各要素に、部材マスタの内部コードを割り当てる（既存の品名と一致すれば自動で候補提示）
- Excelのフォーマットが変更された際も、貼り直すことで更新できる

**日常の起票では数量の並びだけを貼る。品名の並びを貼るのは、フォーマットを登録・更新するときだけ。**
