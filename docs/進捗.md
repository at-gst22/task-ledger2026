### 1.1 「完了」の意味に注意

**上記の ✅ は「一度作った」という意味であり、確定した仕様ではない。**

このプロジェクトは、**業務の実態を手探りで確かめながら進めてきた。**
要件は対話の中で何度も変わっており、実装も**一次的なもの**という位置づけが強い。

実際に変わった例:

- 台帳の置き場所（Box上のExcel → SharePointリスト）
- 台帳への送り方（グリッドビュー貼り付け → ファイル方式に一本化）
- 親の単位（起票 → セッション → 起票に戻す）
- 担当者の持ち方（1名 → 手配主担当＋手配副担当）
- 完了の連動（双方向 → 上げる方向のみ）
- マスタの持ち方（外部JSON → HTMLに埋め込み、自己再生成）

**利用者から要望が出れば、今後も容易に変わりうる。**
「もう決まったこと」として扱わず、変更の依頼を前提に構えること。

**変更に強くするための設計はしてある。**

- 画面の文字・項目名・必須指定・組み立て規則は、すべてマスタで変えられる
- 部材数・部材群数・フォーマットの要素数が変わっても、実装は触らない
- ステータスの流れとリードタイムは、実装ではなくマスタが持つ

**それでも足りない変更は出る。** そのときは実装を書き直してよい。
ただし **`docs/要件.md` §1.5「実装が正本となる領域」を必ず先に読むこと。**
要件書に書かれていない挙動が、実装にだけ存在する。

不採用にした案とその理由は `PROJECT.md` §9 に残してある。
**同じ議論を繰り返さないために、まずそこを見ること。**

### 2.3 具体的な進め方

**`docs/リスト構築手順.md` の第0段階から始める。**

```
第0段階  仕組みの確認   … 最小の1リストで試す。10分
第1段階  一括構築       … フロー1本で全リストを作る。30分
第2段階  仕上げ         … 一意制約・表示名・書式・ビュー・権限。30分
```

**第0段階を必ず先にやること。** 確認するのは1点だけ。

```
リストの設定 → 「起票ID」をクリック → アドレスバーを見る

  ✓ ...&Field=TicketId          ← 成功。第1段階へ
  ✗ ...&Field=_x8d77__x7968_ID  ← 失敗。そこで止めて報告
```

**内部名が英字になるかどうかが、この方式を採る唯一かつ最大の理由。**
ここが崩れたら設計から見直しになるため、10分で先に確かめる。
