### 1.1 「完了」の意味に注意

**上記の ✅ は「一度作った」という意味であり、確定した仕様ではない。**

このプロジェクトは、**業務の実態を手探りで確かめながら進めてきた。**
要件は対話の中で何度も変わっており、実装も**一次的なもの**という位置づけが強い。

実際に変わった例:

- 台帳の置き場所（Box上のExcel → SharePointリスト）
- 台帳への送り方（グリッドビュー貼り付け → ファイル方式に一本化）
- 親の単位（起票 → セッション → 起票に戻す）
- 担当者の持ち方（1名 → 手配主担当＋手配副担当）
- 完了の連動（双方向 → 上げる方向のみ）
- マスタの持ち方（外部JSON → HTMLに埋め込み、自己再生成）

**利用者から要望が出れば、今後も容易に変わりうる。**
「もう決まったこと」として扱わず、変更の依頼を前提に構えること。

**変更に強くするための設計はしてある。**

- 画面の文字・項目名・必須指定・組み立て規則は、すべてマスタで変えられる
- 部材数・部材群数・フォーマットの要素数が変わっても、実装は触らない
- ステータスの流れとリードタイムは、実装ではなくマスタが持つ

**それでも足りない変更は出る。** そのときは遠慮なく実装を書き直してよい。
不採用にした案とその理由は `PROJECT.md` §9 に残してあるので、
同じ議論を繰り返さないために、まずそこを見ること。

### 2.3 具体的な進め方

**`docs/リスト構築手順.md` の第0段階から始める。**

```
第0段階  仕組みの確認   … 最小の1リストで試す。10分
第1段階  一括構築       … フロー1本で全リストを作る。30分
第2段階  仕上げ         … 一意制約・表示名・書式・ビュー・権限。30分
```

**第0段階を必ず先にやること。** 確認するのは1点だけ。

```
リストの設定 → 「起票ID」をクリック → アドレスバーを見る

  ✓ ...&Field=TicketId          ← 成功。第1段階へ
  ✗ ...&Field=_x8d77__x7968_ID  ← 失敗。そこで止めて報告
```

**内部名が英字になるかどうかが、この方式を採る唯一かつ最大の理由。**
ここが崩れたら設計から見直しになるため、10分で先に確かめる。

### 2.4 会社側で必要なファイル

| ファイル | いつ使うか |
|---|---|
| `docs/リスト構築手順.md` | 手順そのもの |
| `src/lists_definition.json` | 第1段階 1-2 で変数に貼り付ける |
| `src/list_formatting.json` | 第2段階 2-3 で書式設定に貼り付ける |

`kihyou.html` と `master_editor.html` は、まだ配置しなくてよい。

### 2.5 第1段階でつまずきやすい点

- **アクション名を `ForEachList` / `ForEachField` に変える。**
  式がその名前を参照するため、既定の「Apply to each」のままだと動かない
- **同時実行を1にする。** 並列だと列の作成順序が狂う
- 途中で失敗したら、できたリストを消してから作り直す

## 3. あわせて確認したい未確認事項

構築の過程で分かるものを、優先順に並べる。

| # | 内容 | 見るところ | 影響 |
|---|---|---|---|
| 1 | 内部名が英字になるか | 構築手順 第0段階 0-4 | **方式そのもの** |
| 2 | **ユーザー型の列で複数値が使えるか** | 手配副担当の列設定 | 副担当の持ち方が変わる |
| 3 | 一意制約が一度で効くか | 構築手順 第2段階 2-1 | 手順が1つ増えるだけ |

通知フロー側で分解する形へ変更する。

その他の未確認事項は `docs/環境台帳.md` の「未確認事項」に集約してある。

## 4. その先の見通し

### 4.1 取り込みフロー（未着手）

```
起票受付ライブラリ → 取り込み → 手配起票 / 手配タスク / 手配明細
```

- トリガーは「ファイルが作成されたとき」（標準）
- 書き込みは `SharePoint に HTTP 要求を送信します`（標準）
- 起票IDで重複を判定し、取り込まない場合もファイルを状態別フォルダへ移す
- 版数の識別子を検証し、許可されていない版は取り込まない

**手動実行用のフローも1本作る。** リンクを開いて実行するだけで即時反映できるようにする
（`docs/要件.md` §3.15.2）。

設計側は「アクションと設定値の表」を用意する。

## 5. 引き継ぐAIへの注意

### 5.1 読む順番

```
1. PROJECT.md      … 前提・制約・役割分担・匿名化ルール
```

- **実データを含むファイルをリポジトリに置く**（`PROJECT.md` §4）
- 成果物のHTMLに、環境を示唆する記述を入れる（`PROJECT.md` §11.3）
- 会社側から外部へファイルを上げる

### 5.3 決まっていること・決まっていないこと

**決まっている**（`docs/要件.md` に記載済み）

台帳の3層構造 / 起票の流れ / 分割ロジック / 通知5種 / 融合・分割 /
論理削除 / マスタの構造 / バージョン管理 / 完了の連動

**決まっていない**

- 検収の自動クローズと、親の完了判定の噛み合わせ（§5.8.4）
