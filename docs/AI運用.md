# AI運用.md — 開発フローとファイルの置き場所

版: v1.0 / 最終更新: 2026-08-12

前提・制約は `PROJECT.md`、現在地は `docs/進捗.md` を参照。
本書は**誰が何を担当するか**と**ファイルをどこに置き、どう受け渡すか**をまとめる。

---

## 1. 2つの環境

**環境は2つに分かれており、直接連携できない。**

| | 開発側 | 実行環境側 |
|---|---|---|
| 位置づけ | **設計と実装の場** | **実行と検証の場** |
| 使えるAI | Web版 Claude Code / ローカル Claude Code / Codex | **Cowork のみ** |
| 制約 | ほぼなし | **強い制約あり（§1.2）** |
| 対象システム | 触れない | SharePoint / Power Automate / Teams / Box |

### 1.1 実行環境側で使えるAIは Cowork だけ

**これは重要な前提。** 実行環境側には Claude Code も Codex もない。

したがって、

- **設計と実装は必ず開発側で行う**
- 実行環境側でコードを書かせない。書かせると、そこにだけ存在する変更が生まれ、
  次の配布で静かに上書きされる
- 実行環境側の Cowork は、**手と目に徹させる**

### 1.2 実行環境側は制約の強い環境である

**「開発側でできることが実行環境側でもできる」と考えてはならない。**
実際に、以下の制約が確認されている。

| 制約 | 内容 |
|---|---|
| **AIが1種類だけ** | Coworkのみ |
| **プレミアムライセンスなし** | Power Automate の「HTTP要求の受信時」が使えない |
| **外部への持ち出し不可** | ファイルを外へ出せない。復路は写真のみ |
| **リポジトリは取得専用** | ログインできないため、ZIPで落とすだけ |
| **PCの性能差が大きい** | グリッドビューへの貼り付けで応答不能になる端末がある |
| **画面操作は人まかせ** | 現状すべて人が行っている（§4.1 に見直しの余地あり） |

**開発側は、この差を常に意識すること。**
「動くはず」と思った機能が使えなかった例が何度もある。
判明した事実は `docs/環境台帳.md` に集約してある。**設計の前に必ず読むこと。**

## 2. 開発側のフロー

```
Web版 Claude Code
  ↓ GitHub
ローカル Claude Code
  ↓ 実装指示
Codex
  ↓ 実装結果
ローカル Claude Code
  ↓ GitHub
Web版 Claude Code
```

**受け渡しは必ず GitHub を経由する。**
会話履歴やチャットの文脈を、受け渡しの手段にしない。

### 2.1 ブランチの扱い

**Web版がpushする際、作業ブランチが作られる場合がある。**

- **特定のブランチへの直接pushを前提にした手順にしない**
- 受け渡しの際は、**GitHub上の正しい最新のブランチと変更状態を確認**してから作業する

### 2.2 廃止した方式

**チャットから成果物をダウンロードし、人がローカルへ配置する方式は廃止した。**

Web版 Claude Code が GitHub を直接読み書きできることを確認済みのため、
人手を介する必要がなくなった。

## 3. それぞれの役割

### 3.1 Web版 Claude Code — 上流工程

| 担当 |
|---|
| ユーザーとの要件・仕様の相談 |
| 仕様書・設計書の作成と更新 |
| GitHub上の最新状態の確認 |
| 現在位置と未決事項を踏まえた、次の実装内容の決定 |
| `docs/implementation-request.md` への実装依頼の記入 |
| GitHubへの反映 |

### 3.2 ローカル Claude Code — 司令塔・最終レビュー

| 担当 |
|---|
| GitHubから取得した仕様・設計・実装依頼の確認 |
| 現在のソースコードとの整合性確認 |
| **実装方針の決定** |
| Codexへの実装指示 |
| Codexの実装結果のレビュー |
| テスト結果と既存機能への影響の確認 |
| `docs/進捗.md` の更新 |
| 実装依頼の履歴化 |
| **許可された場合の commit / push** |

**コード変更を伴う実装は、原則として自分では行わず Codex へ委任する。**

### 3.3 Codex — 実装

| 担当 |
|---|
| 指示に基づくコードの実装 |
| 既存コードの修正・リファクタリング |
| デバッグ・テスト |
| 指摘された問題の再修正 |

**独断で仕様を変更しない。** 詳細は `AGENTS.md`。

### 3.4 実行環境側

| | 担当 |
|---|---|
| **Cowork** | ローカルファイルの読み取りと要約、検証用ファイルの作成・配置 |
| **人** | **画面操作（リスト・フロー・通知の構築）、撮影** |

### 3.5 GitHub — 正本

```
仕様 / 設計 / 環境情報 / 現在位置 / 実装依頼 / 実装依頼履歴 / ソースコード
```

**会話の記憶ではなく、ここが正本。**

## 4. 改善の余地

### 4.1 実行環境側のCoworkに画面操作をさせられるか【未検証・最有力】

**現状、リストやフローの画面操作はすべて人がやっている。**

以前は「エージェントは画面を操作できない」と考えていたが、
**これは検証した結果ではない。** 製品としては画面操作に対応するとされている。

**もし動けば、以下が自動化できる。**

| 作業 | 現在の見積 |
|---|---|
| リストの構築 | 1.5時間 |
| **フローの構築（8本）** | **2〜4時間** ← 最大の工数 |
| 書式設定の貼り付け | 30分 |

**確認方法**（10分程度）

```
1. 実行環境側のCoworkに「ブラウザを開いて、○○のリストを表示して」と頼む
2. 実行できるか、権限を求められるか、できないと言うかを見る
```

**注意**: 画面操作の可否は、アプリの設定と環境のポリシーの両方に依存する。
また、**業務システムを自動操作させることの是非**は、規程の確認が必要。

### 4.2 実行環境側のマスタ更新をCoworkに任せられるか【検討価値あり】

マスタの更新は実行環境側で完結する（§6.4）。現状は人が画面を操作している。
4.1 が成功すれば、この作業もCoworkに任せられる可能性がある。

## 6. 受け渡しの方法

### 6.1 開発側の中での受け渡し

**GitHub を経由する。**（§2）

```
Web版が実装依頼を書く → GitHubへ反映
  ↓
ローカルが取得 → 整合性を確認 → Codexへ指示
  ↓
Codexが実装 → ローカルがレビュー
  ↓
ローカルが文書を更新 → 許可を得てGitHubへ反映
```

**受け渡しの前に、GitHub上の正しい最新のブランチと変更状態を確認すること。**

### 6.2 リポジトリ → 実行環境

**この経路は従来どおり。変更していない。**

```
1. ブラウザでリポジトリを開く
2. Code → Download ZIP
3. 展開して所定のフォルダへ置く
```

**個別ファイルを拾わず、常にフルセットで取得する。**

### 6.3 実行環境 → 開発側

**この経路も従来どおり。写真のみ。** ファイルの持ち出しは行わない。

流すのは「環境の仕様」と「症状」だけ。判明した仕様は、
開発側が `docs/環境台帳.md` を更新する。

### 6.4 マスタの更新（実行環境側で完結）

```
master_editor.html
  マスタを編集 → JSONを保存またはコピー
      ↓
kihyou.html?admin=1
  JSONを貼る → 検証 → 新しい起票ツールを保存
      ↓
Box に置く → 次に開いた人から新しいマスタになる
```

**この経路にリポジトリは登場しない。**
実データを含むため、リポジトリに置いてはならない。

## 7. 実装依頼の受け渡し

### 7.1 ファイル

```
docs/implementation-request.md          … 現在の依頼
docs/implementation-history/
  README.md                             … 運用ルールと連番の規約
  v00_<短い件名>.md                     … 完了した依頼
  v01_<短い件名>.md
```

### 7.2 規約

- **連番は v00 から。** ゼロ埋め2桁
- **完了済みの履歴は原則変更しない。** 追加・修正が必要になった場合は、
  **新しい実装依頼として扱う**
- 依頼が完了したら、`implementation-request.md` はテンプレートへ戻す

詳細は `docs/implementation-history/README.md` を参照。

## 8. 版数の管理

| 対象 | 版数の付け方 |
|---|---|
| 各文書 | 冒頭に `版: 0.9` の形で記載 |
| 起票ツール | マスタの `version`。画面上部に表示される |
| マスタ | 同上。ハッシュ8文字も併記される |

**起票ツールの出力には識別子が入る。**

```
TLV|<版数>|<出力日時>|<マスタのハッシュ>
```

取り込みフローがこれを検証し、許可されていない版は取り込まない。
許可する版数は「許可バージョン」リストで管理する。
