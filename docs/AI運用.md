# AI運用.md — 使っているAIの役割と、ファイルの置き場所

版: v0.3 / 最終更新: 2026-08-12

前提・制約は `PROJECT.md`、現在地は `docs/進捗.md` を参照。本書は**どのAIに何をさせるか**と
**ファイルをどこに置き、どう更新するか**をまとめる。

---

## 1. 2つの環境と、そこで使えるAI

**環境は2つに分かれており、直接連携できない。**

| | 自宅 | 会社 |
|---|---|---|
| 位置づけ | **設計と実装の場** | **実行と検証の場** |
| 使えるAI | **チャット（Opus）** と **Code** | **Cowork のみ** |
| 制約 | ほぼなし | **強い制約あり（§1.2）** |
| 対象システム | 触れない | SharePoint / Power Automate / Teams / Box |

### 1.1 会社側で使えるAIは Cowork だけ

**これは重要な前提。** 会社側にはチャットもCodeもない。

したがって、

- **設計と実装は必ず自宅側で行う**
- 会社側でコードを書かせない。書かせると、会社側にだけ存在する変更が生まれ、
  次の配布で静かに上書きされる
- 会社側のCoworkは、**手と目に徹させる**

### 1.2 会社側は弱い環境である

**「自宅でできることが会社でもできる」と考えてはならない。**
実際に、以下の制約が確認されている。

| 制約 | 内容 |
|---|---|
| **AIが1種類だけ** | Coworkのみ。設計に使える対話AIがない |
| **プレミアムライセンスなし** | Power Automate の「HTTP要求の受信時」が使えない |
| **外部への持ち出し不可** | ファイルを外へ出せない。復路は写真のみ |
| **リポジトリは取得専用** | ログインできないため、ZIPで落とすだけ |
| **PCの性能差が大きい** | グリッドビューへの貼り付けで応答不能になる端末がある |
| **画面操作は人まかせ** | 現状すべて人が行っている（§3.1 に見直しの余地あり） |

**設計側は、この差を常に意識すること。**
「動くはず」と思った機能が使えなかった例が何度もある。
判明した事実は `docs/環境台帳.md` に集約してある。**設計の前に必ず読むこと。**

### 1.3 自宅側にOpusがあることが、この分担の理由

会社側にも判断できるAIがあれば、そちらで完結させたほうが速い。
**そうしていないのは、会社側に設計を担えるAIがないため。**

```
自宅（Opus）  … 迷う作業。設計・判断・診断・実装
会社（Cowork）… 決まった作業。実行・確認・報告
```

## 2. それぞれの役割

### 2.1 自宅側

| | 何者か | 担当 |
|---|---|---|
| **チャット（Opus）** | 対話 | 要件の議論、方針の判断、**写真の読み取りと診断**、成果物の作成 |
| **Code** | リポジトリを操作するエージェント | リポジトリへの反映、匿名化の点検、コミット、push |

**分かれ目は「リポジトリを触るかどうか」。**
チャットはリポジトリに書き込めない。ファイルを作って渡すだけ。
Codeはリポジトリを直接触れるが、設計判断はしない（`CLAUDE.md` で制約している）。

### 2.2 会社側

| | 担当 | 実績 |
|---|---|---|
| **Cowork** | ローカルファイルの読み取りと要約、検証用ファイルの作成・配置 | あり |
| **人** | **画面操作（リスト・フロー・通知の構築）、撮影** | 全て |

### 2.3 CodeとCoworkの関係

**同じ仕組みの上に、入口の違う2つの形として提供されている。**

- **Code** … リポジトリ・git・ターミナルを前提とした開発向けの入口
- **Cowork** … ローカルのファイル、フォルダ、アプリを横断する業務向けの入口。
  **画面操作にも対応するとされている**

「Code＝プログラマー専用、Cowork＝それ以外」という分け方は正確ではない。
**どちらも同種の作業をこなせる。**

**このプロジェクトで役割が分かれているのは、製品の性能差ではなく、
どちらの環境に置かれているかによる。**

### 2.4 判断の基準

```
迷っている作業        → チャット（自宅）
決まっている作業      → Code（自宅） または Cowork（会社）
リポジトリを触る作業  → Code（自宅）
リポジトリ外の作業    → Cowork（会社）
画面操作              → 人（会社）
```

**写真は必ずチャットへ。** 診断した結果を、CodeやCoworkへの短い指示に変換する。

### 2.5 Cowork（会社）に守らせている制約

```
- 設計判断・コード修正は行わない
- 手順にないことは実施しない
- 推測で埋めず、分からないものは「不明」とする
- 業務データ、実在の案件名、個人名は使用しない
```

**理由**: 実装は自宅側で行うため、両方で書くと同じファイルに別々の変更が生まれ、
上書き事故が起きる。

### 2.6 Code（自宅）に守らせている制約

`CLAUDE.md` に記載。

```
- 作業前に必ず PROJECT.md を確認する
- 設計変更・仕様判断は行わない。指示された修正のみ実行する
- 判断に迷ったら、勝手に決めず質問する
- 匿名化ルールを厳守する
- push前に匿名化を自己点検する
```

**この制約は実際に機能している。** 版の履歴の順序が狂っていた件は、
Codeが「指示された修正のみ実行」を守りつつ報告してきたことで発見できた。

## 3. 改善の余地

### 3.1 会社側のCoworkに画面操作をさせられるか【未検証・最有力】

**現状、SharePointやPower Automateの画面操作はすべて人がやっている。**

以前は「エージェントは画面を操作できない」と考えていたが、
**これは検証した結果ではない。** 製品としては画面操作に対応するとされている。

**もし動けば、以下が自動化できる。**

| 作業 | 現在の工数 |
|---|---|
| リストの構築 | 30分 |
| **フローの構築（7本）** | **2〜4時間** ← 最大の工数 |
| 書式設定の貼り付け | 30分 |
| ビューの作成 | 30分 |

**確認方法**（10分程度）

```
1. 会社側のCoworkに「ブラウザを開いて、○○のリストを表示して」と頼む
2. 実行できるか、権限を求められるか、できないと言うかを見る
```

**注意**: 画面操作の可否は、アプリの設定と環境のポリシーの両方に依存する。
また、**業務システムを自動操作させることの是非**は、規程の確認が必要。

### 3.2 CoworkにCodeの役割を兼ねさせるか【検討価値あり】

Coworkもファイル操作とgitを扱えるため、**Codeの役割を吸収できる可能性がある**。

ただし現状、Codeで困っていることはない。**動いているものを変える理由が薄い。**
統合するなら、3.1が成功して役割が整理できてからでよい。

### 3.3 チャットの文脈が切れる問題【対策済み・運用注意】

チャットは会話が長くなると古い部分から失われる。

**対策**: 決定事項は必ず `docs/` へ落としてpushする。
新しいチャットは `PROJECT.md` と `docs/進捗.md` を読んで復帰する。

**運用上の注意**: 同じ会話の中で、更新後のファイルを読み直せない。
URLがキャッシュされるため。**パスの異なるURLを人が提示する必要がある。**

## 5. 更新の方法

### 5.1 自宅 → リポジトリ

```
1. チャットがファイルを出力する
2. ダウンロードして、作業用フォルダの所定の場所へ置く
3. チャットが出す「Codeへの指示」をコピーする
4. Claude Code に貼り付ける
5. Codeが差し替え → 匿名化を自己点検 → コミット → push
6. 報告を受け取る
```

**大きな変更は、部分編集ではなくファイル全体を差し替える。**
部分編集は指示の解釈違いで漏れが生じやすい。

### 5.2 リポジトリ → 会社

```
1. ブラウザでリポジトリを開く
2. Code → Download ZIP
3. 展開して所定のフォルダへ置く
```

**個別ファイルを拾わず、常にフルセットで取得する。**

### 5.3 会社 → 自宅

**写真のみ。** ファイルの持ち出しは行わない。

流すのは「環境の仕様」と「症状」だけ。判明した仕様は、
チャットが `docs/環境台帳.md` の更新版を出し、Codeがpushする。

### 5.4 マスタの更新（会社側で完結）

```
master_editor.html
  マスタを編集 → JSONを保存またはコピー
      ↓
kihyou.html?admin=1
  JSONを貼る → 検証 → 新しい起票ツールを保存
      ↓
Box に置く → 次に開いた人から新しいマスタになる
```

**この経路にリポジトリは登場しない。**
実データを含むため、リポジトリに置いてはならない。

## 6. 版数の管理

| 対象 | 版数の付け方 |
|---|---|
| PROJECT.md / 各文書 | 冒頭に `版: 0.8` の形で記載 |
| 起票ツール | マスタの `version`。画面上部に表示される |
| マスタ | 同上。ハッシュ8文字も併記される |

**起票ツールの出力には識別子が入る。**

```
TLV|<版数>|<出力日時>|<マスタのハッシュ>
```

取り込みフローがこれを検証し、許可されていない版は取り込まない。
許可する版数は、SharePointの「許可バージョン」リストで管理する。
