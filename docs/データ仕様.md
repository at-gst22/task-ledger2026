# データ仕様.md — 起票ツールの出力とSharePoint列の対応

版: v0.2 / 最終更新: 2026-08-12

**取り込みフローを作るために必要な、唯一の対応表。**

列の定義は `src/lists_definition.json`、フローの構成は `docs/フロー設計.md`、
業務上の意味は `docs/要件.md` を参照。

## 0. この文書の位置づけ

本書は **`src/kihyou.html` の `buildPayload()` を実装と照合して作成したもの**（2026-08-12 時点）。

**照合済みのため、着手前の確認は不要。**
ただし `kihyou.html` を変更したら、**本書も必ず更新すること。**

実物を見たい場合は、起票ツールで1件作り、
「台帳へ送る」→「送信する内容を確認する」で表示できる。

## 1. 出力JSONの構造

### 1.1 全体

```json
{
  "marker": "TLV|0.4.0|2026-08-12T12:34:56.789Z|e3024b23",
  "toolVersion": "0.4.0",
  "masterUpdatedAt": "2026-08-12",
  "masterHash": "e3024b23",
  "exportedAt": "2026-08-12T12:34:56.789Z",
  "tickets": [ ... ]
}
```

| 項目 | 型 | 内容 |
|---|---|---|
| `marker` | 文字列 | `TLV|<版数>|<出力日時>|<マスタのハッシュ>`。**検証に使う** |
| `toolVersion` | 文字列 | マスタの `version`。起票ツールの版数として扱う |
| `masterUpdatedAt` | 文字列 or null | マスタの更新日 |
| `masterHash` | 文字列 | マスタ内容のハッシュ8文字 |
| `exportedAt` | 文字列 | ISO8601 |
| `tickets` | 配列 | **1件以上。0件では出力されない** |

### 1.2 tickets[]

```json
{
  "ticketId": "3f2b8c1a-....",
  "title": "9月分手配_部材群A_追加分",
  "titleBase": "9月分手配",
  "titleSuffix": "追加分",
  "group": "部材群A",
  "groupId": "G-A",
  "formatId": "F-A-1",
  "formatVariant": "社内用",
  "splitConfirmed": true,
  "preRequisiteConfirmed": true,
  "preRequisiteMessages": ["...", "..."],
  "deliveryTo": "〒000-0000\n...",
  "deliveryToUndecided": false,
  "dueDate": "2026-09-30",
  "dueDateUndecided": false,
  "requester": "x@example.com",
  "requesterUndecided": false,
  "mainAssignee": "y@example.com",
  "mainAssigneeUndecided": false,
  "subAssignees": ["z@example.com"],
  "details": [ ... ],
  "tasks": [ ... ]
}
```

| 項目 | 型 | 備考 |
|---|---|---|
| `ticketId` | 文字列 | **UUID。ツールが採番する。重複防止の鍵** |
| `title` | 文字列 | 組み上がった名前 |
| `titleBase` / `titleSuffix` | 文字列 or null | 分解した要素 |
| `group` / `groupId` | 文字列 or null | 部材群の名称とID |
| `formatId` / `formatVariant` | 文字列 or null | **手入力のみの起票では null** |
| `splitConfirmed` | 真偽 | 常に `true`（確認しないと出力できないため） |
| `preRequisiteConfirmed` | 真偽 | 前提条件が0件の場合も `true` にならない点に注意（§1.5） |
| `preRequisiteMessages` | 配列 | 表示した文面。0件もありうる |
| `deliveryTo` | 文字列 or null | **未定のときは null** |
| `dueDate` | 文字列 or null | `YYYY-MM-DD`。**未定のときは null** |
| `requester` / `mainAssignee` | 文字列 or null | **メールアドレス**。未定のときは null |
| `subAssignees` | 配列 | **メールアドレスの配列。0件もありうる** |

**`*Undecided` は「未定」を明示的に選んだ場合に `true`。**
値が null でも `false` の場合がある（未入力のまま送信した場合）。**両者は区別すること。**

### 1.3 tickets[].details[]

```json
{
  "position": 1,
  "manualEntry": false,
  "partCode": "P-000001",
  "partNo": "AAA-001",
  "partName": "品名A 12インチ",
  "classCode": "C10",
  "className": "標準品",
  "quantity": 45,
  "initialQuantity": 45
}
```

| 項目 | 型 | 備考 |
|---|---|---|
| `position` | 数値 or null | フォーマット上の位置。**手入力の場合 null** |
| `manualEntry` | 真偽 | 手入力なら `true` |
| `partNo` | 文字列 or null | **空欄は品番未確定を意味する** |
| `quantity` / `initialQuantity` | 数値 | 出力時点では**必ず同じ値** |

**明細に一意なIDは含まれていない。** フロー側で採番する（§3）。

### 1.4 tickets[].tasks[]

```json
{
  "taskSeq": 1,
  "methodCode": "M-A",
  "methodName": "手配方法A",
  "steps": [3, 4, 5, 6, 7, 8, 9],
  "knowhowStepId": "S-A-01",
  "mainAssignee": "y@example.com",
  "subAssignees": ["z@example.com"],
  "dueDate": "2026-09-30",
  "requiredDates": { "5": "2026-09-16", "4": "2026-09-23", "3": "2026-09-28" },
  "partCodes": ["P-000001", "P-000002"],
  "totalQuantity": 57
}
```

| 項目 | 型 | 備考 |
|---|---|---|
| `taskSeq` | 数値 | **起票内の連番。1から** |
| `steps` | 数値の配列 | 通る段階の番号。名称は `docs/要件.md` §5.1 |
| `requiredDates` | オブジェクト or null | **キーは段階番号の文字列**。納品日が未定なら null |
| `partCodes` | 配列 | このタスクに属する明細の部材コード |

**タスクに一意なIDは含まれていない。** フロー側で採番する（§3）。

**`taskSeq` は、画面に表示される `T1` `T2` の番号とは一致しない。**
画面は期限が早い順に並べ替えて表示するが、出力はその並べ替えを行わない。
**追跡のときに混乱しうる点として、§5 に記録。**

### 1.5 注意すべき挙動

| 事象 | 実際の値 |
|---|---|
| 前提条件が0件の部材群 | `preRequisiteConfirmed` は **false**（`preOk` が空配列のため） |
| 手入力のみの起票 | `formatId` `formatVariant` が null、全明細の `position` が null |
| 納品日が未定 | `dueDate` が null、各タスクの `requiredDates` が null |
| 副担当が不在 | `subAssignees` が空配列 `[]` |

**`preRequisiteConfirmed` の挙動は実装の副作用。**
「前提条件が無いのに未確認扱い」になる。取り込み時に補正するか、実装を直すか要判断。
→ **未決事項として §5 に記録。**

## 3. IDの採番と結びつけ

### 3.1 TaskId

**ツールは出力しない。フローが決定的に生成する。**

```
TaskId = {ticketId} + "-T" + {taskSeq}
  例: 3f2b8c1a-1234-5678-9abc-def012345678-T1
```

**乱数を使わないこと。** 決定的に導けば、同じファイルを二重に取り込んでも
同じIDになり、一意制約が二重登録を弾く。

### 3.2 DetailId

```
DetailId = {ticketId} + "-D" + {配列の添字}
  例: ...-D0, ...-D1
```

**`details` 配列の順序が鍵。** 配列の順序は出力時点で固定されており、
同じファイルを取り込めば同じ順序になる。

### 3.3 明細とタスクの結びつけ

**`partCode` で一意に決まる。曖昧さはない。**

```
明細の partCode を、tasks[].partCodes に含むタスクを探す
  → 必ず1つだけ見つかる
```

**理由**：手配方法は「部材 → 分類コード → 手配方法」で一意に決まるため、
**同じ部材コードが2つのタスクにまたがることがない。**

同じ部材の明細が複数行ある場合（手入力と貼り付けが別行で残った場合）も、
**どちらも同じタスクに属する。** そのまま同じ TaskId を割り当ててよい。

### 3.4 details の並び順

```
貼り付け由来 → 手入力 の順（実装で concat している）
```

**この順序は出力時点で固定される。** 同じファイルを再取り込みしても
同じ DetailId になるため、一意制約が二重登録を弾く。

## 4. 導出項目

### 4.1 リンク列

```
TaskLink   = {サイトURL}/Lists/手配タスク/AllItems.aspx?FilterField1=TicketId&FilterValue1={ticketId}
DetailLink = {サイトURL}/Lists/手配明細/AllItems.aspx?FilterField1=TaskId&FilterValue1={TaskId}
```

**リストの実際のURLは、構築後に確認して差し替えること。**
日本語のリスト名はURLエンコードされる場合がある。

### 4.2 NextDueDate

```
requiredDates の値のうち、まだ到達していない段階のもので最も早い日付
```

- 取り込み時は、**すべての値のうち最も早いもの**を入れる
- **ステータスが進むたびにフローが再計算する**（`docs/フロー設計.md` F7）
- `requiredDates` が null なら空にする

**この列だけが索引付きの日付列。** 遅延判定・絞り込み・並べ替えはすべてこれを使う。

### 4.3 DetailDigest

```
上位3件を「品名×数量」で連結し、残りは件数で示す
  例: 品名A 12インチ×45 / 品名C ケーブル×10 / 品名E 取付金具×2 ほか27件
```

**ツール側では作っていない。フローが組み立てる。**

## 5. 未決事項・留意点（本書由来）

| # | 内容 | 影響 | 判断の時期 |
|---|---|---|---|
| 1 | **`preRequisiteConfirmed` が、前提条件0件のとき false になる** | 取り込み時に補正するか、実装を直すか | フロー設計の前 |
| 2 | **`taskSeq` と画面の `T1` `T2` の順序が一致しない** | 追跡のときに混乱しうる | 実装を直すか、そのままにするか |
| 3 | `titleBase` `titleSuffix` `groupId` `formatId` を列に持つか | 現状は捨てている | 保留でよい |
| 4 | 日本語のリスト名によるURLエンコードの影響 | リンク列が動かない可能性 | 構築後に確認 |

### 5.1 #1 の詳細

```js
preRequisiteConfirmed: (t.preOk.length > 0 && t.preOk.every(Boolean))
```

前提条件が0件の部材群では `preOk` が空配列のままとなり、**`false` が出力される。**
「確認すべきことが無い」のに「未確認」と記録される。

**対処案**：取り込みフローで
`preRequisiteMessages` が空なら `PreConfirmed` を `true` にする、
あるいは実装側の条件を `t.preOk.every(Boolean)` に変える。

### 5.2 #2 の詳細

```
画面（renderSplit）   … 期限が早い順に並べ替えて T1, T2, T3 と表示
出力（buildPayload）  … 並べ替えず、明細に現れた順に taskSeq 1, 2, 3
```

**データの正しさには影響しない。** ただし利用者が「T2を確認した」と認識したものが、
台帳の枝番2とは限らない。

**対処案**：`buildPayload` でも同じ並べ替えを行い、`taskSeq` を振り直す。
実装は数行。**推奨するが、必須ではない。**
