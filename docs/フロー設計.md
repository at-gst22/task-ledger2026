版: v0.2 / 最終更新: 2026-08-12

**すべて未実装・未検証。本書は設計案であり、確定仕様ではない。**

列の定義は `src/lists_definition.json`、JSONとの対応は `docs/データ仕様.md`、

## 0. 前提

### 0.1 使えるもの（環境台帳で確認済み）

| 種別 | 名称 | 判定 |
|---|---|---|
| トリガー | 項目が作成されたとき / 修正されたとき / 削除されたとき | 標準 |
| トリガー | ファイルが作成されたとき（SharePoint） | 標準 |
| トリガー | 選択したファイルの場合 | 標準 |
| トリガー | Recurrence（繰り返し） | 標準 |
| トリガー | 手動でフローをトリガーします | 標準 |
| アクション | SharePoint に HTTP 要求を送信します | 標準 |
| アクション | アダプティブ カードを投稿して応答を待機する | 標準 |
| アクション | ユーザーの @mention トークンを取得する | 標準 |
| **トリガー** | **HTTP 要求の受信時** | **プレミアム。使えない** |

### 0.2 全フローに共通する必須事項

**① ループ防止**

フローがリストを更新すると、そのフローのトリガーが再び発火する。

```
フローの冒頭で「更新者がフローボット自身か」を判定し、
自身による更新であれば何もしない
```

**判定方法は未確定。** `更新者` 列（`Editor`）が接続作成者と一致するかを見る、
あるいは「最終更新の種別」を示す列を持たせる、などの案がある。
**着手前に方法を決めること。**

**② 接続の権限**

フローは常に**接続を作成した人の権限**で動く。
台帳の `登録者` はすべてその人になるため、**実際の起票者は別列で持つ**
（`docs/要件.md` §2.4）。

**③ 通知の投稿先**

チャネルへ投稿する（`docs/要件.md` §9.7）。投稿者は**フロー ボット**。

## 1. フロー一覧

| # | 名称 | トリガー | 役割 | 優先 |
|---|---|---|---|---|
| **F1** | 取り込み（自動） | ファイルが作成されたとき | JSONを3リストへ展開 | **最優先** |
| **F2** | 取り込み（手動） | 手動でフローをトリガーします | 未処理をまとめて取り込む | 高 |
| F3 | 割り当て通知 | 項目が作成/修正されたとき（タスク） | 通知①② ＋ カード応答 | 高 |
| F4 | 納品待ち通知 | 項目が修正されたとき（タスク） | 通知③ | 中 |
| F5 | 納品確認通知 | 項目が修正されたとき（タスク） | 通知⑤ | 中 |
| F6 | 遅延通知 | Recurrence（日次） | 通知④ | 中 |
| F7 | 完了の連動 | 項目が修正されたとき（明細・タスク） | 明細→タスク→起票 | 中 |
| F8 | 検収の自動クローズ | Recurrence（日次） | 2か月経過で終了 | 低 |

**F1が動けば、起票からリストまでが一気通貫になる。** まずここだけを作る。

**F3〜F5は1本にまとめられる可能性がある**（トリガーが同じため）。
分けるほうが切り分けやすく、まとめるほうが構築が速い。**着手時に判断する。**

## 2. F1 取り込み（自動）【最優先】

### 2.1 骨子

```
1. ファイルが作成されたとき（起票受付ライブラリ）
2. 拡張子が .json か確認   → 違えば エラーフォルダへ移動して終了
3. ファイルの中身を取得
4. JSONの解析
5. marker を検証            → 不正なら エラーフォルダへ移動 ＋ 通知
6. tickets を1件ずつ処理（§2.2）
7. 取込済フォルダへ移動
```

### 2.2 ticket 1件の処理

```
a. 起票IDが既に手配起票にあるか確認
     ある → この ticket は飛ばす（重複スキップ）
b. 手配起票に1行作る
c. tasks を1件ずつ
     TaskId を採番（データ仕様 §3.1）
     手配タスクに1行作る
d. details を1件ずつ
     DetailId を採番（データ仕様 §3.2）
     partCode を含む tasks を探し、その TaskId を割り当てる
       → 必ず1つだけ見つかる（データ仕様 §3.3）
     手配明細に1行作る
e. TaskLink / DetailLink / DetailDigest / NextDueDate を設定
```

### 2.3 検証の内容

**補正が1つ必要**：`preRequisiteMessages` が空の場合、
`preRequisiteConfirmed` は `false` で届く（実装の副作用。データ仕様 §5.1）。
**取り込み時に `true` へ補正するかどうかを決めること。**

| 検証 | 不合格のときの扱い |
|---|---|
| 拡張子が `.json` | エラーフォルダへ移動 |
| JSONとして読めるか | 同上 |
| `marker` の形式 | 同上 |
| `toolVersion` が許可バージョンにあるか | エラーフォルダへ ＋ 起票者へ通知 |
| `ticketId` が既に台帳にあるか | **重複スキップフォルダへ移動。エラーではない** |

**取り込まなかった場合も必ずファイルを移動させる。**
受付フォルダの直下に残るものが未処理、という状態を保つため。

### 2.4 Person型への解決

JSONはメールアドレスを持つ。**Person型列にはメールアドレスをそのまま渡せば解決される見込み**だが、
**未検証。** 解決できない場合の挙動（エラーで止まるか、空で入るか）も確認すること。

**副担当は複数値。Person型で複数値が使えるかも未検証**（環境台帳）。
使えない場合は、メールアドレスを改行で連結したテキスト列に変更する。

### 2.5 同時実行

**同時実行数を1にする。** 複数ファイルが同時に置かれたときの競合を避ける。
この規模（1日数件）なら待ちは実感できない。

## 3. F2 取り込み（手動）

**F1と中身は同じ。トリガーだけが違う。**

```
1. 手動でフローをトリガーします
2. 起票受付ライブラリ直下のファイルを一覧取得
3. 1件ずつ、F1 の手順2〜7を実行
```

**単独・複数のどちらのファイルにも対応させる**（`docs/要件.md` §3.15.2）。

**このフローのURLを、起票ツールのマスタ `texts.flowUrl` に設定する。**
利用者はリンクを開いて [実行] を押すだけで即時反映できる。

**未検証**：フローのURLを開いて、その画面から実行できるか。

---

## 4. F3 割り当て通知（通知①②）＋ カード応答

### 4.1 骨子

```
1. 項目が作成または修正されたとき（手配タスク）
2. ループ防止の判定
3. 手配主担当が設定されているか、前回と変わったか
4. @mention トークンを取得（主担当・副担当）
5. アダプティブカードを投稿して応答を待機する
6. 応答者を検証（§4.3）
7. 台帳を更新
8. messageLink を LastCardLink に保存
```

### 4.2 カードの内容

**検証済みの構成**（環境台帳 §H）

```
タイトル      … タスク名
本文          … 納品日 / 数量 / 次の必要作業日
ステータス    … Input.ChoiceSet（次の段階へ進める）
日付          … Input.Date（納期の変更）
コメント      … Input.Text（自由記述）
```

応答は `data.status` `data.newdate` `data.comment` で返る。

### 4.3 応答者の検証

```
応答者 ＝ 手配主担当 または 手配副担当のいずれかか
  一致   → 通常どおり更新
  不一致 → 未決（docs/要件.md §5.6.2 の3案）
```

**カードの応答に応答者を識別できる情報が含まれるかは未検証。**
含まれない場合、この検証はできない。→ 環境台帳の未確認事項 #1

### 4.4 長時間の待機について

**「応答を待機する」はフローが実行中のまま止まる。**
既定のタイムアウトと上限は未確認（環境台帳）。

数日〜数週間待つ運用になるため、**タイムアウトの設定を必ず確認すること。**
実行中のフローが多数溜まることの影響も、運用しながら見る。

## 5. F4 納品待ち通知（通知③）

```
1. 項目が修正されたとき（手配タスク）
2. ループ防止の判定
3. ステータスが「8 納品確認」に変わったか
4. 主担当・副担当へ投稿（応答は待たない）
```

**担当者への最後の通知。** 以後、そのタスクでは担当者へ通知しない
（`docs/要件.md` §9.1）。

---

## 6. F5 納品確認通知（通知⑤）

```
1. 項目が修正されたとき（手配タスク）
2. ループ防止の判定
3. ステータスが「9 検収確認」または完了に変わったか
4. 起票者へ投稿（1回だけ）
```

**宛先は起票者。担当者ではない。**

---

## 7. F6 遅延通知（通知④）

```
1. Recurrence（日次・平日の朝など）
2. 手配タスクから、次の条件で取得
     NextDueDate < 今日 かつ 完了 = いいえ かつ 削除 = いいえ
3. 該当がなければ何もしない
4. まとめて1件投稿する（担当者ごとにメンション）
```

**締め日ごとに複数回飛ぶ**（`docs/要件.md` §9.2）。

**1件ずつ投稿しないこと。** 件数が多いとチャネルが埋まる。
**日次のまとめ投稿**とし、その中で各担当者をメンションする。

## 8. F7 完了の連動

### 8.1 上げる方向のみ

```
明細の手配完了が変わったとき
  → 同じ TaskId の明細がすべて完了か
      すべて完了 → タスクを完了にする

タスクの完了が変わったとき
  → 同じ TicketId のタスクがすべて完了か
      すべて完了 → 起票の状態を「完了」にする
```

**下げる方向は行わない**（`docs/要件.md` §5.8）。

### 8.2 NextDueDate の再計算

**同じフローで扱う。**

```
タスクのステータスが変わったとき
  → RequiredDates から、まだ到達していない段階の最も早い日付を求め
     NextDueDate を更新する
```

### 8.3 ループ防止が最も重要なフロー

**このフローは自分でリストを更新するため、必ず自分のトリガーを再発火させる。**
§0.2 の判定を入れないと、無限ループになる。

### 8.4 未決事項

**検収の自動クローズ（F8）で閉じたタスクを「完了」に数えるか。**
数えないと起票が閉じない。数えると、検収未了のまま起票が完了扱いになる。
→ `docs/要件.md` §5.8.4

---

## 9. F8 検収の自動クローズ

```
1. Recurrence（日次）
2. ステータスが「9 検収確認」かつ、その状態になってから2か月経過したもの
3. 完了にし、AutoClosed に印を付ける
```

**自動で閉じた事実を必ず残す**（`docs/要件.md` §5.4）。

「その状態になってから」を判定するには、**ステータスが変わった日時を保持する列が要る。**
現在の `lists_definition.json` には無い。

→ **未決事項。列を1つ足すか、`更新日時` で代用するかを判断すること。**

## 10. 構築の順序

```
第1段  F1 取り込み（自動）        ← ここが動けば一気通貫になる
第2段  F2 取り込み（手動）        ← F1の複製
第3段  F3 割り当て通知             ← 双方向の要
第4段  F7 完了の連動 ＋ NextDueDate
第5段  F4 F5 F6                    ← 通知の残り
第6段  F8 検収の自動クローズ
```

**F1が動くまで、他のフローを作っても試せない。** 順序を守ること。
